# Expected failures of tests/regression/check_ext_vector_abi_grid.sh,
# measured on ubuntu-24.04 with lccc at this revision and the pinned Clang
# 23.1.3 oracle (two hosted runs). The gate compares its observed failure
# set with this file EXACTLY: a failure not listed here is red, and a listed
# failure that no longer happens is red too (remove the line in the commit
# that fixes it) -- except class `flaky`, see below.
#
# Columns: <bits> <opt> <shape> <provider:caller> <check> <class> <tracking-id>
#   class `oracle`: the clang:clang leg fails the same check, so Clang 23.1.3
#     disagrees with itself and there is no reference for lccc to meet
#     (i386 va_arg of these vector shapes; long double vectors).
#   class `lccc`: Clang agrees with itself and lccc does not meet it,
#     deterministically -- an open lccc ABI defect, tracked under the id:
#     ABI-EXTVEC-LD-I386-1 i386 three-lane long double ext vectors (`ldx3`)
#                          against Clang: `ident`/`kfour` at -O0 and `hash2`
#                          at -O2 disagree cross-compiler (lccc agrees with
#                          itself; the -O2 ident/kfour legs are Clang-broken,
#                          see class `oracle`). Not measurable without the
#                          hosted Clang oracle; the x86-64 lanes are fixed.
#   Retired (fixed): ABI-EXTVEC-LD-1 (x86-64) -- `ldx1` returns were lowered
#     with an I64 return type in the DEFINITION only (the caller popped
#     %st(0), the callee had converted the lane to a double in %rax), and
#     the two-lane `%st(0)/%st(1)` pair return (Clang: `<2 x x86_fp80>` is
#     not an aggregate, so its MEMORY-class return goes "direct" to LLVM and
#     is scalarized onto the x87 stack -- GCC's `_Complex long double`
#     convention) was a hard compile error, and the lanes were 16 bytes
#     apart where Clang (LLVM's `<N x x86_fp80>`) packs them at 10.
#     `ldx2`/`ldx3` arguments now follow the ABI-EXTVEC-VA-1 slot rule
#     (MEMORY at the vector's 32/64-byte alignment). The `hashva` `flaky` rows were the same defects seen
#     through va_arg; lccc <-> lccc is deterministic over 40 stack-shifted
#     runs for all three shapes. GCC 16 compiles the x87 struct / complex
#     side in check_gnu_vector_align_abi.sh (Part 4). The hosted Clang run
#     is the measurement for the cross legs; a residual shows up here as an
#     unlisted failure and must be re-triaged, not re-listed blind.
#   Retired (fixed): ABI-EXTVEC-I386-O2-1 -- not an ABI defect at all but
#     an aggregate_copy_forward miscompile: a forwarded temporary whose
#     source was a PATH into another forwarded temporary (`image + 16`, the
#     second XMM piece of a 32/64-byte i386 ext vector argument) kept
#     reading the deleted copy. Both halves (lccc caller and lccc callee)
#     were wrong independently at -O2 and are fixed; see
#     tests/regression/agg_copy_forward_subobject_chain.c (plain structs,
#     x86-64 too) and the pass unit test.
#   class `flaky`: an open lccc defect whose outcome varies between runs.
#     The gate neither requires nor forbids the failure; it counts how many
#     occurred. No row currently carries this class (the last ones, the
#     x86-64 long double `hashva` legs, were retired with ABI-EXTVEC-LD-1).
#   Retired (fixed): ABI-EXTVEC-VA-1 -- the lccc CALLER placed a MEMORY-class
#     vector argument wider than 16 bytes at a 16-byte-aligned stack slot
#     because the type's alignment was modelled as the capped `_Alignof`
#     figure instead of its size; every callee (Clang, GCC, lccc's own
#     prologue and va_arg) rounds the slot up to the full alignment, so on
#     half of all stack residues the callee read 16 bytes that were never
#     written. The provider:caller pattern recorded here (clang:lccc and
#     lccc:lccc failed hashva, lccc:clang never did) is the caller-side
#     signature. Covered deterministically, against the GCC 16 oracle, by
#     tests/regression/check_gnu_vector_align_abi.sh.
