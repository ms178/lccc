# Follow-up: aggregate snapshots, SIMD forwarding and atomic interop

## Basis and counterexamples

The branch was rebased on main `ad09b96c6f3b6f7c8273834128a04a3ea39148cd` (which includes #1129). The earlier base was `a2ca5caa99dad102e1591b72f69c354f52b33c74`. PR #1126 remained open and red when checked; this work does not alter that PR's branch or claim to resolve its DWARF failures.

On the earlier base, `tests/regression/memcpy_snapshot_alias.c` reproduced a real native x86-64 miscompile: at `-O2`, `-Os` and `-O3` the call variant returned exit 1, while GCC 16.2, Clang 23.1.5 and LCCC `-O0`/`-O1` passed. An intervening call can change the source after the first memcpy; pointer identity checks are not an alias proof. After fixing the first forwarding pass, the aliased-store variant returned exit 2. Disabling aggregate SROA made it pass; pass dumps showed its copy-buffer collapse reading the source after the store. This was a distinct path. Both passes now require equal extents and distinct direct nonvolatile alloca roots for memcpy-to-memcpy collapse, and treat unproven intervening writes, atomics and fences as barriers. This is conservative, not a general alias analysis.

After #1129 merged, its intrinsic consumer needed the same intervening-write guard. For a memory result, this branch additionally requires a distinct nonvolatile direct source and destination alloca: it does not assume that every backend reads all input chunks before writing the result. A result's `vector_home_width()` does not prove the width or role of each argument: scalar operands, addresses, and mixed-width vector operands exist. The new check uses the existing explicit per-operand width table instead, with no `usize` truncation; unknown roles fail closed. IR tests exercise scalar `SetEpi32_256`, scalar `Pinsrd128`, mixed-width `Broadcast128to256`, valid `MinPs256` positions, and oversized lengths. These guards are deliberately stricter than the preexisting optimization; they are not a proof that the rest of #1129 is defect-free.

A further IR-level counterexample uses a GEP that redefines a former alloca value to point into the destination. Treating the old alloca as a unique root may introduce overlap. The new root set rejects multiple definitions; the IR regression covers both forwarding paths. This is a defensive post-SSA case, not a claimed C-level reproducer.

## Evidence and boundaries

* GCC 16.2 and Clang 23.1.5 run the native snapshot test without warnings under `-Wall -Wextra -Werror`; the pre-rebase fixed compiler passed x86-64/i686 at `-O0/-O1/-O2/-Os/-O3` (i686 required explicit cached multilib library paths). After the rebase, the native GCC differential regression passed; AArch64 and RV64 passed all five levels under QEMU.
* The atomic interop test runs LCCC/Clang caller-callee combinations both ways at five optimization levels on AArch64 and RV64, and Clang/Clang controls. A deliberately wrong fetch-add must exit with the exact expected check code. AArch64 includes aligned 128-bit add with low-half carry and strong CAS success/failure and expected writeback; RV64 covers 32/64 bits. These are **sequential** interoperability/value checks; they do not establish contention safety or memory-order mappings, and do not exercise real RV64 128-bit libatomic.
* All 34 interop controls passed, as did 84 existing ABI interop controls. The AArch64 freestanding build initially failed on hosted CI: distributions with Clang outline atomics enabled generated unresolved `__aarch64_*` helper references. Locally reproducing that default with `-moutline-atomics` also failed; `-mno-outline-atomics` on this one fixture restored all 34 controls. This tests the inline LL/SC implementation, not outlined runtime interoperability.
* After rebase, `check_avx256_fp_contracts.py` passed 72 execution/frame checks across GCC 16.2, Clang 23.1.5 and LCCC on x86-64 and i686. For `avx_private_frame`, `objdump` at `-O2 -mavx2` counted 157 instruction rows for this conservative branch versus 36 each for GCC/Clang in this environment. The #1129 report cites 57 for its own final run; that is not a same-run baseline. Instruction counts are not timing or PMU measurements. A trial allowing writes to distinct direct allocas did not change the 157-row result and was discarded; faster safe forwarding remains an open problem.
* Before the main rebase, the full Rust library run passed 8308 tests, with 10 ignored. The prior rebased PR head `e00c11157` completed all executed GitHub checks successfully, including Clippy, SSA, assertion-enabled corpus and authenticated ICX integration; that result does not apply to subsequent commits. The operand-role change passed the focused copy-propagation and 44 vector-temp tests. A final same-tree local gate and hosted CI remain required.
* An initial `ci_local.sh --fast` was stopped after multiple i686 link failures (`-lgcc`) and a host GCC `-m32` preflight failure. A verified, matching Bookworm `lib32gcc-12-dev` package was extracted **only to an isolated /var/tmp sysroot**, not installed into `/`; `LCCC_SYSROOT` plus verified GCC 16 library paths then made both the previously failing type-attribute gate and IVSR i686 preflight/gate pass. This does not convert the interrupted run into a pass; repeat the entire gate in the corrected environment.
* Local audit census and the parameter-home contract passed on the earlier base; census also passed on the rebased changes. The parameter-home result does not establish the status of #1126's older head.
