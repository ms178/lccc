## 09-15 — `.gnu.hash` parity on five backends + RELRO + riscv DT_NEEDED
<!-- src: FOLLOWUP-2026-09-15-gnuhash-relro-crossarch.md -->

Measured oracle truth (20k absent probes): lld nbuckets = n/4, bloom =
next_pow2(n/4), shift 26 (FPR ≈0.4–0.6 %); mold ≈ n/8; bfd wants a
per-link records and 1–2 %; **old lccc: one bloom word, shift 6 — the
bloom filter died above ~30 exports (~1.0 false-positive at 20k)**.
Land rule (helper `linker_common::hash.rs`): `bloom_words = max(1,
next_pow2(ceil(n/4)))` — power of two required, glibc masks the word
index with `size-1`; `shift = lg2(bloom_words × class_bits)`;
`nbuckets = max(1, n/4)`. At n=3000 lccc-built `.so` is byte-identical
to lld's geometry with fewer total bytes than bfd/lld/mold. Bloom
carries the false-positive rate (lld's 8-bits-per-symbol budget);
buckets only bound chain length — bfd's 2× buckets are strictly worse.
Same pass: RELRO page-rightsizing fixed on riscv, landed on aarch64;
riscv `-l` `DT_NEEDED` generation; hidden defects found while doing it
(two, fixed in the same series). Validation: 239/0/0 linker suite. [goal][fix]

## 09-16 — kernel 6.18.52 retarget + the vDSO PHDRS blocker (GNU parity fix)

Retargeted every kernel harness script from linux-cachymod 6.18.50 to
**6.18.52** (upstream archpkgbuilds already builds `_minor=52`); the
fresh tree takes all 29 CachyMod patches and the 32 KiB setup gate
passes on the first try (`_end`=31168, headroom 1600 B, flat setup.bin
byte-identical to the ld.bfd oracle).

**The full bzImage build then died at `vdso2c: cannot handle memsz !=
filesz`** — first PHDR-level defect of the kernel quest on the
`-T`-script path. Chain: the vDSO script declares `note PT_NOTE` in its
PHDRS clause while also placing a real allocated `.note` output section;
`emit_script.rs` counted an auto PT_NOTE for that section **on top of**
the declared one, so `e_phnum` and the file-offset seeding disagreed
with the headers actually written (phantom fifth NULL phdr). Because
SIZE_OF_HEADERS seeded 4 headers while file offsets seeded 5, the first
section's congruence rule (`file_off ≡ lma mod page`, forward-only)
jumped a page — `.hash` vaddr 0x120 / offset **0x1120** — and the sole
PT_LOAD came out with p_filesz 0x26a6 > p_memsz 0x16a6.

Measured GNU semantics on binutils 2.44 (five-case parity matrix,
reproduced in the commit message): **a declared PHDRS block means GNU ld
emits exactly the declared headers — no auto PT_NOTE, no auto
PT_GNU_PROPERTY, no auto PT_TLS; auto-headers exist only on the
implicit-segment path.** The fix gates the PT_TLS synthesis, the
note/property synthesis, their SIZEOF_HEADERS prediction and the
post-layout count on `script.phdrs.is_empty()`, making prediction,
count and emission identical by construction in both paths. This also
removed a silent SIZEOF_HEADERS divergence: a `.tdata` under
`PHDRS{text}` used to shift every section address away from GNU's for
the same script.

Validation: kernel vdso64.so.dbg links with exactly 4 phdrs,
filesz==memsz, 0 dynamic relocations, vdso2c produces the image C file;
new regression test `script_vdso_declared_note_phdrs` (linker suite
**240/240**) pins the phdr set, filesz==memsz, and the
offset==vaddr congruence of every allocated section in both the lccc
and GNU outputs. [fix][goal]

## 09-17 — MachInst sub-word reload fix: the vsnprintf phantom-NUL root cause

The kernel's `%d`/`%u` output was corrupted from the very first boot
print: every decimal number was emitted with a leading NUL byte
(`SMBIOS \0 2.\0 8`, `node \0 0`, `\0 97 pages`) while `%x`/`%p` were
clean. The same defect produced the kobject "empty name" symptom
(write("%d") returning 2 with `{0x00,'0'}`) that the previous session
chased through put_dec/decpair — decpair loads were innocent all along.

**Root cause** (x86 MachInst window allocator, `machinst_alloc.rs`):
an *arriving* sub-word vreg was reloaded from its slot with a partial
register write (`movb slot, %r11b`), but the rest of the pipeline —
home moves (`movq %r11, %rdi`), full-width store-backs
(`movq %rdi, slot`), and S64 `Test`/`Cmp` operands — reads every GP
vreg as a full 64-bit register image (the invariant `value_to_reg`
upholds classically: U8 → `movzbl`, I8 → `movsbq`). In `number()` the
`char sign` was reloaded with `movb` into a register whose upper bits
still held `(unsigned)(field_width - 1)` — 0xFFFFFF00 for the default
width 0 — so the 64-bit `if (sign)` test saw a nonzero image and
stored sign byte 0x00 ahead of the digits. Signed char builds were
never affected because the `if (sign)` test compiled to `cmpb` there;
the kernel uses `-funsigned-char`, which selected the 64-bit test.
The 4-byte-slot promotion already reloaded at `movl` "which defines
the full register" — S8/S16 reloads violated exactly that discipline.

**Fix**: `arriving_reload()` — sub-word arriving reloads now emit
zero-/sign-extending forms (U8 `movzbl`, I8 `movsbq`, U16 `movzwl`,
I16 `movswq`); S32+ unchanged (`movl` already zero-extends). Store-back
keeps the narrow transfer. The small-slot S32 clamp semantics are
preserved (width decided from the clamped `transfer_size`, signedness
from the IR type).

**Why the static audits missed it**: the relocation audit and the
normalized disasm comparison proved the *kernel objects* identical to
fresh compiles of the same source with the same flags — i.e.
determinism, not correctness vs the C source. The host harness linked
the same .o files but ran them under different register pressure: the
defect needs the exact window/register split the kernel build produced.
`CCC_NO_MACHINST=1` / `CCC_MI_ALL_CLASSIC=1` / `CCC_NO_REGALLOC_FUNC=`
all "fixed" it — bisection by env knob isolated the window allocator;
`CCC_MI_STREAM` + a byte-exact od(1) of the serial log localized the
bad image.

Validation: new regression test
`tests/regression/machinst_subword_reload_sign.c` (reduced number()
shape, `-O2 -funsigned-char`) FAILS 5 cases on the old compiler and
PASSES on the fixed one; new unit test
`subword_arriving_reload_defines_full_register` pins the movzx/movsx
reload forms; `cargo test` 2862 passed; linker suite 241/241; ci_local
--fast ALL GATES GREEN; full kernel rebuild + QEMU boot clean of
phantom NULs. [fix][goal]

Also this session: after an Arena restore the work tree was re-based
onto upstream main (which had moved); the S02/S03 linker work (vdso

(`Cmp Eq V27,V56`); the miscompile was pure backend: in
`__get_file_rcu` (fs/file.c, 6.18.52) the `OPTIMIZER_HIDE_VAR`
asm (`"" : "=r"(out) : "0"(in)`) compared a leftover `=@ccns`
boolean chain in %rcx against the file pointer in %r12 — the tie
load of `in` was never emitted.

**Root cause**: `load_input_to_reg` (x86-64 asm_emitter) handled
`Operand::Value` inputs by loading from their STACK SLOT only. When
the tied input value is register-homed WITHOUT a slot (value
forwarding kept the fresh `Load *f` in %r13), the load was silently
skipped — the asm operand register kept whatever it held. Same
latent hole in i686 and ARM (RISC-V had the home path but silently
skipped home-less+slot-less values).

**Fix (5 files)**:
- x86-64: no-slot inputs materialise via `value_to_reg` (fresh/stale
  homes, width-consistent typed loads, Copy/bit-identical Cast
  chains, GlobalAddr remats; panics loudly otherwise).
- `value_to_reg_inner`: added the accumulator (rax) last-resort
  fallback before the final panic, mirroring `operand_to_callee_reg`.
- i686: no-slot inputs load from their authoritative linear-scan home
  (`movl %home, %reg`); 64-bit pairs and home-less+slot-less values
  panic loudly.
- ARM: no-slot inputs `mov` from `reg_assignments` home (RISC-V-style);
  FP/no-home panic loudly.
- RISC-V: home-less+slot-less inputs panic loudly (was silent skip).

**Validation**:

## Session S09 — defect (h) fixed and boot-validated (2026-09-18)

**Root cause of (h), finally pinned**: not the parser, not
type_builder, not sema. The lowerer's `sizeof_deref`
(src/ir/lowering/expr_sizeof.rs) clamped every pointee resolving to
size 0 up to 1 (`if sz == 0 { return 1 }`), and `sizeof_subscript`
clamped every element size with `.max(1)` — stale guards from the
era before the GNU `sizeof(*void_ptr) == 1` / `sizeof(*func_ptr) ==
1` extensions got their own explicit match arms just above. GNU C
zero-length arrays are legitimately size 0 and GCC preserves that
through every spelling: direct decl `char (*p)[0]`, typedef
`typedef char T0[0]; T0 *q`, struct field (the kfifo `rectype`
idiom), subscript, nested `[0][N]`, cast, typeof. The clamp made
`__kfifo_max_r` compute recsize 1 for every plain kfifo, so
kfifo_in/out took the record path and the 8250 xmit kfifo delivered
userspace serial one byte per record — the "garbled ttyS0" from the
S08 session was a kfifo record-mode corruption, not an n_tty
ONLCR/echo bug (that was the S08 suspicion, wrong branch).

**Fix**: remove the clamp in `sizeof_deref`'s Pointer and Array arms
and all nine `.max(1)` in `sizeof_subscript` (both subscript
directions + the member-access fallback). The genuine 1s keep their
explicit arms. Pointer-arithmetic strides and compound-literal
element sizing stay clamped by design (a 0 stride in generated
scaling code would loop; nothing in the kernel needs a 0 stride).
Audited clean alongside: `sizeof_type`, `sizeof_identifier`,
`sizeof_member_access`, sema `sizeof_expr`/`size_ctx`,
`resolve_ctype_size` — none clamp.

(C1) `build_demoted_select_arm`, a recursive arm demotion reusing every
