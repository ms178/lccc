## 2026-10-18 — scalar<->vector conversion diagnostics + ext-vector splat lowering

After a rebase onto `644f4145` (PR #862 vectorizer wave), an oracle-driven
red-team sweep of the vector semantic space against gcc-16.2.0 /
clang-23.1.3 found a pair of genuine pre-existing defects and one latent
miscompile class; all three are fixed with oracle-matched diagnostics.

* **Scalar <-> GNU `vector_size` conversions.** Both oracles reject
  explicit casts between a vector and a scalar of different size in either
  direction (GCC: "cannot convert a value of type 'int' to vector type
  '__vector(1) double' which has different size"), and reject implicit
  scalar<->vector assignments/initialisations at ANY size (the
  documentedly-divergent exception: Clang accepts a same-size
  vector->scalar implicit conversion as a raw reinterpretation; GCC
  rejects it -- lccc implements the GCC verdict, with the divergence
  recorded in the gate header). lccc silently accepted every one of these
  shapes -- and for the accepted ones the lowering used the scalar
  rvalue's VALUE as the SOURCE ADDRESS of the whole-vector copy
  (witness: `b = i;` on `vector_size(4)` float emitted `movl (%rax)`
  with %rax == 5, faulting at run time). Sema now diagnoses all of them,
  in `check_assignment_compatibility` (assignments/returns), the cast
  arm of `analyze_expr` (explicit casts, GCC wording in both directions)
  and scalar object initialisation.
* **Ext-vector scalar splat miscompiles (two sites, one class).**

  assignment form `v = 2.5f;` shared the same address-confusion defect as

  Both are lowered as a value operation now: the scalar is converted to
  the lane type and stored into each lane (`copy_vector_expr_to_alloca`,
  `lower_vector_assign`), mirroring the existing swizzle splat.

## 2026-10-22 — Dual-layout metric pairs on every backend, and RS-1

Follows `2026-10-21-dual-layout-metric-parallel.md` (the x86-only split, now
merged). Two things were wrong with stopping there.

**The split was x86-only for no reason.** `peephole_for_metric` is a real text
peephole in all four backends — `peephole_optimize` over each arch's own
assembly — and `relayout_blocks_static_chain` explores on every target at
`-O1`+, so i686, AArch64 and RISC-V were paying the same two serial pass mixes.
The scheduling policy (floor, host probe, knob, counters, candidate labels) now
lives in one arch-neutral module, `backend::metric_pair`, and each backend
supplies a three-line override passing its own `peephole_optimize`. The shared
default in `ArchCodegen` stays serial and says why: it is called through
`&mut dyn ArchCodegen`, so a default body cannot prove `Self: Sync` and cannot
hand a candidate to a worker.

**RS-1: RISC-V was not reproducible.** Found while checking the new identity
contract across backends — five *serial* compilations of one source produced
five different assemblies. The identical-block pass grouped blocks in a
`std::collections::HashMap` and iterated `groups.values()`, so the per-process
hash seed decided which duplicate label survived a retarget; `.Lskip_N` numbers
and block placement moved between runs. Fixed by using the tree's `FxHashMap`
(two sites, lookup-plus-iteration). A backend-tree audit found exactly one
order-dependent iteration besides it (an i686 `iter().any(...)`, order-safe by
construction). Reproducible builds, cached objects and every `diff`-based gate
depend on this, so the new gate now compiles each fixture three times per
backend and requires one hash.

## 2026-10-28 — two follow-up investigations not landed (and why)

Two further runtime ideas were measured and deliberately held back; the
traps are recorded so they are not re-derived.

1. Never-read DSE vs vectorized reduction spills (`loop_patterns`). The
   vectorized widening reductions emit nine `movdqu %xmmN, off(%rsp)`
   stores whose slots have no plain reload. Root cause is two stacked
   conservative bails in `dead_code::eliminate_never_read_stores`, not the
   store analysis: (a) the no-FP prologue backscan from `subq` terminates
   on the first interleaved `.cfi_offset` directive — a fix that steps over
   code-less `.cfi_*` lines is sound and unit-testable, but is inert alone;
   (b) the function's variadic `printf` lowers to a body-interior
   `pushq $0; pushq %r12; call; addq $16,%rsp`, an rsp shift that bails the
   whole function until the pass tracks an rsp delta across the balanced
   region. A crude textual "unreferenced slot" scan over-reported dead
   stores in `sha256_transform` and `glibc_memcmp`: those slots ARE read,
   via an SIB index (`8(%rsp,%r8,4)`) and a `leaq` floor respectively, which
   the real pass correctly attributes. No DSE code changed.

2. Packed-FP load folding (`f32_sse1_map`, `nbody`, `matmul`, ...).
   Extending `memory_fold::fold_fp_register_loads` from scalar `movss/movsd`
   to packed `movups/movaps` folds an adjacent load into `addps/mulpd/...`,
   matching Clang. First cut folded `movups` into LEGACY packed arithmetic
   and SIGSEGV'd ten differential-corpus programs (rc=-11): a legacy packed
   arithmetic m128 memory operand REQUIRES 16-byte alignment and #GP-faults
   on an unaligned address, whereas `movups` may legally be unaligned. The
   sound rule — aligned `movaps/movapd` may fold into legacy or VEX,
   unaligned `movups/movupd` only into VEX (no alignment requirement),
   width-matched, with the existing CFG liveness proof — passes the full
   corpus but changes ZERO of 78 benchmark and 1133 regression TUs, because
   codegen currently emits `movups` plus legacy SSE arithmetic and never the
   aligned/VEX pair the rule needs. The runtime win therefore belongs
   upstream (vectorizer/isel emitting `movaps` on proven-aligned addresses,
   or alignment-aware folding), not in a text peephole; the change was
   reverted rather than ship a never-firing path.

## 2026-10-28 — Never-read DSE across in-body RSP shift windows (lands item 1 above)

The deferred DSE item above is now implemented in
`peephole/passes/dead_code.rs` and validated. Both conservative bails it named
are relaxed with explicit soundness rules rather than a blanket allowance:

1. **CFI backscan** (`subq` prologue): step over code-less `.cfi_*`
   directives, stopping on `cfi_startproc`/`cfi_def_cfa_offset` or any non-CFI
   directive. In the live pipeline earlier passes strip the `.cfi_offset`
   lines before DSE, so this alone has zero effect; it is the combination with
   delta tracking that matters.
2. **RSP-delta model.** A constant signed depth (push/subq +, pop/addq −) is
   carried through the body; every `%rsp` frame read translates back to its
   canonical slot (`off − delta`); `%rbp` operands are untouched. Fail-closed
   cases: a store or SIB frame operand at non-zero delta, an unparseable
   non-epilogue shift, a conditional/indirect branch at non-zero delta, a
   memory-form push/pop (`pushq 0(%rsp)` reads a slot while shifting), and a
   shifted unconditional `jmp` whose target block accesses the frame.

Three trap families the original investigation did not anticipate were found
by the differential corpus and encoded as rules, each with a mutation-tested
unit test:

- **Loop back-edge labels live inside open push windows** (cmpxchg retry
  loops): a label must NOT reset the linear delta, or a post-`pop` read maps to
  the wrong canonical slot and a live store is deleted (`param_prestore`).
- **A label after a path-ending `ret`/`jmp` IS a canonical-depth boundary**:
  the next block is reached only by a forward branch at canonical depth, while
  the prior epilogue's negative delta would otherwise carry in (cpuid inline
  asm block, `asm_static_inline_pointer_outputs`). Pure-linear and
  reset-every-label are both wrong; the discriminator is whether the linear
  path terminated.
- **Escaped frame pointers index both ways**: the bounded "floor" model's
  upward-only assumption breaks when a sign-extended (negative) index feeds a
  derived `leaq` (`sse2_i32_product`, `bb_slp_v7`, `cond_reduction`). These
  were already safe in the old model only because the in-body shift bail
  skipped the whole function; the path-end reset keeps them correctly handled.

Blast radius: 1/78 benchmark TUs (`loop_patterns`, nine dead `movdqu` stores
deleted, `.text` −128 B, deletions only) and 13/1182 regression TUs, all
deletion-only. Differential corpus 1195/0, all-targets tests 6772/0, clippy
and rustfmt clean. Paired CPU-pinned wall clock: eight 21-rep A/B runs on the
one affected kernel, min geomean 0.9899 (−1.01 %), median −1.02 %, 6/8 faster;
low3 geomean −0.80 %; full 56-kernel suite geomean 1.0005 (neutral, no
regression). A modest, repeatable gain on the affected hot loop plus a
soundness/code-size improvement, not a broad uplift — reported as such rather
than overclaimed. Frozen artifacts:
`engineering/evidence/dse-rsp-delta-2026-10-28/`.

## 2026-10-28 — alignment-proven movaps/movdqa assessed, not pursued (metric trap)

Re-examined the deferred "emit aligned SSE moves on proven-aligned slots"
item with a fresh census and a direct microbenchmark rather than the earlier
displacement-only analysis. Across the 78 benchmark TUs there are 49 frame
vector moves, all `%rsp`-based: 37 at `disp % 16 == 0` (provably aligned at

`(disp + rsp_delta) % 16 == 0` for `%rsp`, `disp % 16 == 0` for `%rbp`,

miscompiles too, and `CCC_NO_PEEPHOLE=1` is correct *with the sibling call still

breaking at labels (gcc.c-torture 981130-1, 980526-2); this shape has no label,
only the epilogue. Prefer retiring the orphan at the conversion site (one block
per call site is the invariant the whole marker protocol rests on) over teaching
the reader first-marker-wins, which touches every peephole that consults call

argument-free call, a call consuming the pointer, and a final void call eligible

### DWARF alignment attribute: the encoding, and what D6/D7 bought

`DW_AT_alignment` is **0x88**. **0x21 is `DW_AT_is_optional`**, and writing 0x21
fails *silently in a way that looks like success*: the abbreviation table stays
valid, the value is emitted in the right place, readelf decodes the record's
third attribute as `DW_AT_is_optional : 64`, and pahole simply reports no forced
alignments. Confirm a producer's attribute code by parsing its **decompressed**
`.debug_abbrev` (`objcopy --decompress-debug-sections`, then walk the ULEB pairs)
— `readelf -x` shows the compressed bytes and cannot be used, and gcc's default
here is `-gz` (its `.debug_abbrev` starts with the zlib magic `78 9c`).

With that fixed and D6 (zero-length arrays as `DW_AT_count`, not
`DW_AT_upper_bound`) in place, pahole's report for `struct netns_ipv4` on
`net/ipv6/addrconf.o -gdwarf-4` is character-for-character identical to gcc-16's:
`size: 896, cachelines: 14, members: 163`, `sum members: 780, holes: 15, sum
holes: 100`, `padding: 16`, `forced alignments: 4, forced holes: 2, sum forced
holes: 64`, closing `} __attribute__((__aligned__(64)));`. Before, it reported
`char x[1]` for each `__cacheline_group_*` marker, `sum members: 788` and
`BRAIN FART ALERT! 896 != 788 + 98`.

Residual DWARF gaps, measured on that same TU (lccc vs gcc-16): 21 151 vs 24 441
DIEs (0.865×) — lccc emits less debug information; lccc does not compress debug
sections while gcc's default `-gz` does, so a naive object-size comparison
*inverts* the truth (610 KB uncompressed vs 1 410 KB compressed); and
`DW_AT_alignment` scope differs in **both** directions — on a small probe
(`#pragma pack`, natural/lower/equal/raised field alignment, alignment via
typedef, nested aligned struct, aligned global and array) lccc emits 8 and gcc 11,
the 3 missing being exactly the typedef and the two variable DIEs, while on the
kernel TU lccc emits *more* on records and members (576 vs 435), so its
user-alignment predicate is broader than gcc's `TYPE_USER_ALIGN`/`DECL_USER_ALIGN`
for kernel shapes the probe does not contain.

emitted block with **no incoming edge**. In the rcu case the orphaned block is a

jmp <join>`) that nothing branches to, so that warning can never fire. The IR has

and the object has 11 `ud2` sites, so it is a lost edge, not duplication. It
survives `CCC_NO_PEEPHOLE=1` (object grows 157 768 → 166 560 B, orphan unchanged)

either compiler, so the trigger is the surrounding CFG (66 IR blocks including a
`Switch`).

**Measurement trap.** Reachability must account for fallthrough: an instruction
after a *conditional* jump is reachable. Counting only explicit branch targets
reports 10 of those 11 `ud2` blocks as orphaned; the correct answer is 1.

The third (`io_uring/io-wq.o: io_wq_worker+0x4eb: io_worker_exit() missing
__noreturn`) is a **missed inlining opportunity**, not an annotation gap.
`io_worker_exit` is a local static with exactly one call site; converting the call
to a tail jump is impossible because `io_wq_worker` returns `void *`/NULL while
the callee returns `void`, so inlining is the only transformation that removes the
call. objtool's dead-end inference is correct and its `missing __noreturn` wording
is generic. The fourth (`lib/iov_iter.o:
copy_compat_iovec_from_user+0x10b: return with UACCESS enabled`) is not
root-caused; D3 removed its 8 siblings so it is not the macro-shadowing defect.

### Performance, measured with the sanctioned harness

`scripts/bench_kernels.py` at `-O3`, best-of-7, interleaved arms, driver compiled
once by a fixed reference compiler, output verified per arm (no correctness
failure): **geomean 1.222× vs gcc-16** (lccc faster), 0.802× vs clang. Wins:
`memchr` 43.34× (lccc vectorises, gcc-16 does not; 0.43× the `.text`),
`namechars` 3.61×. Regressions: `seg_gs_copy` 0.53×, `strcmp_signed` 0.70×,
`varint` 0.71×, `sqlite_varint_scan` 0.78×, `bn_mul128` 0.86×, `base64_decode`
0.89×. Total `.text` across the 22 kernels is 0.94× gcc's, and size does not
predict speed in either direction (`map64_sub` 1.62× the size but 1.33× faster;
`strcmp_signed` 0.40× the size but 0.70× the speed), so both columns have to be
reported together.

`seg_gs_copy` is root-caused: in `seg_copy_pass` lccc emits **132 instructions
against gcc-16's 14** — 43 `movdqu` where gcc uses 4 `movdqa` + 4 `movaps`
despite both arrays being `__attribute__((aligned(32)))`, **32 scalar `movq`**
moving 32-byte aggregates 8 bytes at a time, 28 `leaq`, and a loop body that
opens by spilling index-derived values to fixed stack slots on every trip
(`leaq 3(%r14),%rax; movq %rax,48(%rsp); leaq 4(%r14),%rax; movq %rax,40(%rsp)`).
Three separable losses: a live-range/rematerialisation defect (cheapest win),
alignment not reaching move selection, and incomplete lowering of aggregate
copies to full-width moves.

The largest absolute gap found is not gcc-relative: `strlen_scan` runs 141.471 ms
under lccc and 142.020 ms under gcc-16 but **0.085 ms under clang** — a SIMD
`strlen` idiom neither lccc nor gcc-16 recognises at `-O3`, with lccc's `.text`
at 0.23× gcc's, so it is a missing idiom rather than a size problem.

### The census is closed, and the seg_gs_copy loop body read in full

`objtool` refuses to re-check an object that already carries `.static_call_sites`
and such an object reports **no warnings at all**, so a census total is only
trustworthy if none of the skipped objects would have warned. All 24 skipped
objects were therefore re-measured properly: each TU recompiled from its own
`savedcmd_<obj> := …` line into a **fresh** object outside the tree (leaving the
in-tree object that caused the skip untouched), then objtool run on that. All 24
compiled rc=0 and produced **0 warnings**, so the census closes at **4 warnings
over the comparable 1357 objects** with nothing hidden. This also proves the D3 fix
honestly: `arch/x86/kernel/smp.o` is among the 24 and its 2 earlier `redundant
UACCESS disable` warnings are genuinely gone rather than masked by the skip.

Reading lccc's emitted loop body for the worst regression (`seg_copy_pass`,
`.LBB18 → .LBB19`) corrects the headline number and sharpens the diagnosis. lccc
**unrolls the loop by 4** (128 bytes per trip, pointers advanced with
`leaq 128(%rbp)`/`128(%r15)`/`128(%r12)`), so the fair comparison is per element:
**109 instructions per trip / 4 elements = 27.25 against gcc-16's 10**, i.e. 2.7×,
not the 13× that the raw 132-vs-14 function totals suggest. Inside that body:
8 `movdqu %xmmN, K(%rsp)` spills against only **3** reloads, so 5 spilled values
are never reloaded; 10 `movq %rN, K(%rsp)` address-materialisation stores against
12 loads; **8 stores are dead outright** (4 xmm + 4 GPR, the slot is overwritten
before anything reloads it); 25 `leaq`; 30 scalar `movq`. Even the loop *counter*
is round-tripped — the body opens with
`leaq 3(%r14), %rax; movq %rax, 48(%rsp); leaq 4(%r14), %rax; movq %rax, 40(%rsp)`
and closes with `movq 40(%rsp), %r14; cmpq $256, %r14; jl .LBB18`, where gcc-16
does `addq $32, %rax` on an induction variable that never leaves a register.

The 8 dead stores survive because `eliminate_dead_pure_writes`
(`src/backend/x86/codegen/peephole/passes/dead_writes.rs:227`) filters its
candidate on `plain_gp_operand(dst)` and `is_writable_family_gpr(fam)`, so it only
ever considers a **general-purpose register destination**; an xmm destination and
a memory destination such as `16(%rsp)` are structurally out of scope, and the
same holds for `eliminate_dead_flag_writes` (`:154`). The deeper difference is
addressing: gcc-16 folds `bench_seg_src` and `gen_blk` into `symbol+offset(%rax)`
operands on one induction variable using zero stack slots, while lccc
re-materialises each address with `leaq` and routes it through a stack slot.
