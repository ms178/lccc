## 2026-10-18 — scalar<->vector conversion diagnostics + ext-vector splat lowering

After a rebase onto `644f4145` (PR #862 vectorizer wave), an oracle-driven
red-team sweep of the vector semantic space against gcc-16.2.0 /
clang-23.1.3 found a pair of genuine pre-existing defects and one latent
miscompile class; all three are fixed with oracle-matched diagnostics.

* **Scalar <-> GNU `vector_size` conversions.** Both oracles reject
  explicit casts between a vector and a scalar of different size in either
  direction (GCC: "cannot convert a value of type 'int' to vector type
  '__vector(1) double' which has different size"), and reject implicit
  scalar<->vector assignments/initialisations at ANY size (the
  documentedly-divergent exception: Clang accepts a same-size
  vector->scalar implicit conversion as a raw reinterpretation; GCC
  rejects it -- lccc implements the GCC verdict, with the divergence
  recorded in the gate header). lccc silently accepted every one of these
  shapes -- and for the accepted ones the lowering used the scalar
  rvalue's VALUE as the SOURCE ADDRESS of the whole-vector copy
  (witness: `b = i;` on `vector_size(4)` float emitted `movl (%rax)`
  with %rax == 5, faulting at run time). Sema now diagnoses all of them,
  in `check_assignment_compatibility` (assignments/returns), the cast
  arm of `analyze_expr` (explicit casts, GCC wording in both directions)
  and scalar object initialisation.
* **Ext-vector scalar splat miscompiles (two sites, one class).**
  `ext_vector_type v = 2.5f;` in a declaration initialiser and the
  assignment form `v = 2.5f;` shared the same address-confusion defect as
  above (Clang-documented legal splat; crashed instead of broadcasting).
  Both are lowered as a value operation now: the scalar is converted to
  the lane type and stored into each lane (`copy_vector_expr_to_alloca`,
  `lower_vector_assign`), mirroring the existing swizzle splat.
* **Regression net.** New gate `check_vector_scalar_conversions.sh`:
  nine reject shapes verified against BOTH pinned oracles (with the one
  measured GNU/Clang divergence recorded), plus running positive controls

* **Environment work for the local oracle set.** Deleted the stale 2 GiB

## 2026-10-22 — Dual-layout metric pairs on every backend, and RS-1

Follows `2026-10-21-dual-layout-metric-parallel.md` (the x86-only split, now
merged). Two things were wrong with stopping there.

**The split was x86-only for no reason.** `peephole_for_metric` is a real text
peephole in all four backends — `peephole_optimize` over each arch's own
assembly — and `relayout_blocks_static_chain` explores on every target at
`-O1`+, so i686, AArch64 and RISC-V were paying the same two serial pass mixes.
The scheduling policy (floor, host probe, knob, counters, candidate labels) now
lives in one arch-neutral module, `backend::metric_pair`, and each backend
supplies a three-line override passing its own `peephole_optimize`. The shared
default in `ArchCodegen` stays serial and says why: it is called through
`&mut dyn ArchCodegen`, so a default body cannot prove `Self: Sync` and cannot
hand a candidate to a worker.

**RS-1: RISC-V was not reproducible.** Found while checking the new identity
contract across backends — five *serial* compilations of one source produced
five different assemblies. The identical-block pass grouped blocks in a
`std::collections::HashMap` and iterated `groups.values()`, so the per-process
hash seed decided which duplicate label survived a retarget; `.Lskip_N` numbers
and block placement moved between runs. Fixed by using the tree's `FxHashMap`
(two sites, lookup-plus-iteration). A backend-tree audit found exactly one
order-dependent iteration besides it (an i686 `iter().any(...)`, order-safe by
construction). Reproducible builds, cached objects and every `diff`-based gate
depend on this, so the new gate now compiles each fixture three times per
backend and requires one hash.

Re-measured on current main (`973ae6b3b`, `rustc 1.97.0`, `fastbuild`, 2
effective threads, `scripts/measure_peephole_pair.py --arms serial,auto,forced
--iters 15 --warmups 3`, medians of paired ratios, seeded bootstrap intervals,
assembly hashed every run):

| backend | fixture | pairs (split) | auto/serial [95 % CI] |
|---|---|---|---|
| x86-64 | 6 benchmark TUs (median) | 10 (10) | **0.854** (0.854 / 0.854 / 0.842 / 0.857 / 0.896 / 0.838) |
| x86-64 | `peephole_pair/chain_wide.c` | 10 (10) | **0.758** [0.712, 0.794] |
| i686 | same | 10 (10) | **0.941** [0.896, 0.957] |

| riscv64 | same | 10 (10) | 1.027 [0.953, 1.052] → **neutral** (below) |

**The harness had an order bias, and it mattered.** Arms ran in a fixed order
(`serial` first, always), which lets CPU frequency drift and page-cache warming
bias one arm. It produced a *sign flip* on one TU: `expat_siphash24` measured
1.021 [1.011, 1.031] inside a six-source batch and 0.871-0.912 measured alone,
minutes apart. The script now shuffles the arm order per iteration from a
seeded RNG (reproducible record), and the same TU then reads 0.854 [0.843,
0.869] in a batch, consistently with its standalone value. Every number above
was produced with the randomised order; the earlier tables in this entry were
fixed-order and their per-TU values should be read as +/- one arm-order bias.

**RISC-V is neutral, not faster.** Its 15-iteration 1.027 is noise: the compile
is only ~70 ms, so a 0.5 ms total saving sits under the scheduler. A decisive
60-iteration run gives 0.986 [0.967, 1.001] and 0.994 [0.977, 1.019] — the
interval straddles 1.0, i.e. no measurable effect either way. It is left
enabled rather than special-cased: the split is provably output-neutral there,
costs nothing measurable, and a per-arch floor would be a knob justified by
data that does not exist. Its pass mix is roughly an order of magnitude cheaper
than x86-64's (~160 us saved per pair against a ~50 us spawn), which is the
whole explanation.

**Throughput closed.** The previous entry left `make -j` unmeasured. A
saturated 2-job build of the same six TUs (two compilers at a time = the
host's effective width) gives serial 0.419 s vs auto 0.420 s, ratio **1.0023**:
the extra transient thread is invisible under saturation, which is the one
place it could have cost something.

records incl. the per-iteration ratio vectors, `x86-benchmarks.json`). Gate:
`tests/regression/check_peephole_pair_parallel.py`, covering all four backends
plus the reproducibility contract; it drives the cross backends with a
header-free fixture so it needs no cross sysroot.

Gate coverage, second pass: the first version fired one pair per cross backend
(whatever a compact probe happens to trigger) and only at `-O1`. It now uses

stopped counting would still pass an identity-only check while proving nothing
about which path ran. The compact probe was deleted once the wide fixture

RS-1 sweep, completed: every `std::collections::HashMap`/`HashSet` binding in a
codegen path was enumerated and each iteration site inspected. Besides the two

emitting (`sort_by_key`), and the single i686 iteration is a boolean
`iter().any(..)`. Nothing else in the codegen path can reorder output from a
randomized hash seed.

## 2026-10-22 — Differential coverage for object identity and value survival

**Base:** `d31e9ae9cd00152c946e3353b3f1a3d04f67d76b`. The two x86-64 backend
defects fixed just before this base (alloca-address truncation; the stale
accumulator cache on the U64→FP path) were found by hand, and no engine in
`tests/fuzz` could have found either: `slot_rmw` fuzzes slot *homes*,
`punning` fuzzes *bytes*, and nothing generated `(cast)(uintptr_t)&local` or a
double conversion of one integer value. This entry adds that coverage instead
of leaving the fix protected only by two hand-written regression files.

**New engine.** `tests/fuzz/addr_value_fuzz.py` emits self-checking
translation units: every function takes the address of its own local, checks an
invariant about it, and prints `OK` or `FAIL <name>`, so the reference
compiler's own `OK` is the oracle and nothing about the harness changes.
Address shapes: cast chains (one chain applied to *both* sides of the
comparison), scalar assignment, array base, runtime index, struct/union/`memcpy`
round trip, `noinline` argument, ternary, loop, byte-window pointer difference,
padded struct member, 16-byte vector local. Conversion shapes: repeat
conversion, source survives, two routes to the same conversion, copy
before/after, interleaved integer use, exact round trip, over sources on the
big path (`x ^ (1ULL << 63)`), the plain unsigned path, a negative signed route
and both narrow routes.

The anti-vacuity rule is the important design point: `f(&s) == f(&s)` also
holds in a compiler that lowers `&s` to `s`, so every case additionally asserts
`(uintptr_t)s != (uintptr_t)&s`. The first draft of the standalone probe did the
opposite (different cast chains on the two sides) and failed under GCC — the
generator is now validated by the reference compiler in
`tests/fuzz/test_addr_value_fuzz.py` (13 tests: determinism, seed sensitivity,
shape reachability, the anti-vacuity invariant, "no absolute address leaves its
function", UB-free initialisers, reference agreement at -O0/-O2, and the
`reference_rejected` → `skip` path).

**Wiring.** `addr_value` is the 16th `scripts/fuzz_diff.py` engine
(`--engine addr_value`, defaults 60 seeds / seed 0 / `-O0..-Os` / gcc), with a
new `oracle: "reference"` spec class: the ELF32/int80 host probe and the
`-m32` compile-only fallback belong to the m32 family and must never gate this
hosted engine (before this entry every non-`self_model` forwarding engine fell
through that probe). Smoke gates: the new step in `ci.yml` and the
`addr-value-fuzz-smoke` gate in `scripts/ci_local.sh` (8 seeds × 3 levels);
`scripts/check_ci_gate_parity.py` PASS (342 commands).

**Measurements** (GCC 16.2 oracle, 200 seeds × 5 levels = 1000 arms):
1000 PASS, 0 mismatch, 0 compile failure, 0 skip; Clang 23.1.3 as the compiler
under test 300/300 PASS. Sensitivity, measured against a rebuilt pre-fix tree
(`0ab6e743`, both defects present): 85 of 300 arms fail, spread over the
address shapes and the conversion shapes at `-O0`/`-O1` (the accumulator-cache
defect does not reproduce at `-O2`+), so the engine is not vacuous. Corpus
UB-freedom: 60 seeds build and run clean under UBSan+ASan with the host GCC
12.2 — the pinned GCC 16.2 and Clang 23.1.3 caches ship no compiler-rt, so that
check stays a manual gate. ICX 2026.2 was not installed in this session and is
therefore not claimed.

**Limits.** The engine covers `-m32` not at all (the m32 engines own that
target) and does not generate cross-function address oracles on purpose:
comparing a callee's address with a caller's local compares two different stack
slots and proves nothing. Fuzzing, not proof: the invariants are properties any
correct implementation satisfies, not a specification of every lowering.

## 2026-10-26 — GCC 16.2 default dialect, function prototypes, and AVX2 replay

The active `arena/5ae2882a-lccc` branch now defaults to GNU C23, matching GCC
16.2's no-flag `__STDC_VERSION__=202311L`; explicit `-std=gnu17` continues to
select `201710L`. The frontend/type pipeline now preserves whether an empty
function parameter list is a prototype separately from its parameter count.
This is required because `f()` is a zero-parameter prototype in C23 but an
unspecified-parameter declaration in earlier modes, while `f(void)` is a
prototype in both. The distinction reaches direct declarations, definitions,
function pointers and pointer typedefs. A GCC 16 differential also exposed a
conditional-expression bug: choosing the then-arm type discarded a prototype
when an unprototyped function pointer was the then arm. Composite-type building
now preserves a compatible prototype from either arm (and merges compatible
array bounds); positive and negative GNU17 call cases across LCCC, GCC 16.2 and Clang 23.1.3,
plus common-type unit tests, pin it.
K&R function-body parameter types stay separate from the visible call
prototype, and function compatibility follows the default-promotion rule where
a prototype meets an unprototyped type.

Differentials: GCC 16.2 and LCCC agree on direct and function-pointer
extra-argument rejection in default GNU23 and acceptance in GNU17; both reject
an extra argument to `(void)` in GNU17. Clang 23.1.3 agrees under explicit
`-std=gnu23` and `-std=gnu17` (its no-flag default remains GNU17). The
`__builtin_types_compatible_p` probe agrees across LCCC/GCC/Clang: GNU17
`1 1 0 0 0`; GNU23 `1 0 0 0 0`. No compatibility banner or GCC version macro
was changed: dialect matching is one measured facet, not full GCC 16.2 parity.

The old MB-11 per-function `target("avx2")` reduction concern was also
replayed. `tests/regression/per_function_target_avx2_reduction/reduction.c`
now pins a signed i32 reduction that emits YMM code only inside the
target-attributed function, with a neighboring baseline twin kept YMM-free.
At `-O2`, YMM
references in the target body were LCCC 13, GCC 16.2 2, Clang 23.1.3 8; the
baseline body had zero for all three. The target and baseline functions both

this branch; instruction-reference counts are not a runtime-performance claim.
