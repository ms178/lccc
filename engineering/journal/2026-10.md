## 2026-10-18 — scalar<->vector conversion diagnostics + ext-vector splat lowering

After a rebase onto `644f4145` (PR #862 vectorizer wave), an oracle-driven
red-team sweep of the vector semantic space against gcc-16.2.0 /
clang-23.1.3 found a pair of genuine pre-existing defects and one latent
miscompile class; all three are fixed with oracle-matched diagnostics.

* **Scalar <-> GNU `vector_size` conversions.** Both oracles reject
  explicit casts between a vector and a scalar of different size in either
  direction (GCC: "cannot convert a value of type 'int' to vector type
  '__vector(1) double' which has different size"), and reject implicit
  scalar<->vector assignments/initialisations at ANY size (the
  documentedly-divergent exception: Clang accepts a same-size
  vector->scalar implicit conversion as a raw reinterpretation; GCC
  rejects it -- lccc implements the GCC verdict, with the divergence
  recorded in the gate header). lccc silently accepted every one of these
  shapes -- and for the accepted ones the lowering used the scalar
  rvalue's VALUE as the SOURCE ADDRESS of the whole-vector copy
  (witness: `b = i;` on `vector_size(4)` float emitted `movl (%rax)`
  with %rax == 5, faulting at run time). Sema now diagnoses all of them,
  in `check_assignment_compatibility` (assignments/returns), the cast
  arm of `analyze_expr` (explicit casts, GCC wording in both directions)
  and scalar object initialisation.
* **Ext-vector scalar splat miscompiles (two sites, one class).**
  `ext_vector_type v = 2.5f;` in a declaration initialiser and the
  assignment form `v = 2.5f;` shared the same address-confusion defect as
  above (Clang-documented legal splat; crashed instead of broadcasting).
  Both are lowered as a value operation now: the scalar is converted to
  the lane type and stored into each lane (`copy_vector_expr_to_alloca`,
  `lower_vector_assign`), mirroring the existing swizzle splat.
* **Regression net.** New gate `check_vector_scalar_conversions.sh`:
  nine reject shapes verified against BOTH pinned oracles (with the one
  measured GNU/Clang divergence recorded), plus running positive controls
  (equal-size explicit cast prints the lane bit pattern 1092301619;
  constant and non-constant splats), wired into ci.yml and ci_local.sh
  fast tier.  All ten pre-existing ext-vector gates re-ran green
  (swizzle diagnostics, rvalue subscript, size, narrow arith, one-lane
  fp, ABI wide 10-config, callsite ABI, lane1 ABI, ABI grid 954 legs
  0 defects, ext codegen).
* **Environment work for the local oracle set.** Deleted the stale 2 GiB
  swapfile (the new 8 GiB `/swapfile2` is active); installed
  g++-multilib/lib32stdc++-12-dev from the harness debs cache and the
  multiarch asm symlink, un-skip-ing the linker suite's i386 C++ leg
  (302 passed / 0 failed, two skips left: ld.bfd >= 2.45 pin and the
  kernel.org `relocs` tool -- both network-pinned artefacts). Provisioned
  the pinned GAS 2.47 oracle pair (`as` + `objdump`) for x86_64 and
  aarch64 under `$HOME/.cache/gas-2.47-*` by building from the harness's
  hash-verified binutils 2.47 source tree: x86-asm-diff 1418/1418,
  i686-asm-diff 672/672, encdiff-corpus histogram baseline matches,
  both semantic-validation suites green -- four previously-red ci_local
  gates closed, all residual reds are network-attributed
  (godbolt.org TLS-block, git.kernel.org, arm.com XML).
* Incidental oracle data points: equal-size scalar<->vector explicit
  casts are the raw bit reinterpretation in both directions across all
  three compilers; scalar->vector assignment splat is rejected by BOTH
  oracles for plain `vector_size` (ext-vector splats excepted); the
  floppy r2 witness (`f1 b; b = i;` faulting) was caused by mid-edit
