## Pointer induction legality

A constant comparison alone does not bound an unsigned counter. A 32-bit counter with stride `1 << 30` and `i != (1 << 30) + 1` wraps without reaching its bound, while pointer induction variables continue advancing. On a sparse 4-GiB mapping the upstream compiler with the pass enabled timed out; the pinned GCC 16.2 oracle and LCCC with the pass disabled both returned the expected result. The regression touches only a few pages but requires sufficient 64-bit virtual address space; a failed mapping or timeout is a test failure, not a skip.

The legality proof checks which comparison edge actually returns to the header, the comparison operation, exact step of the comparison's recurrence increment, source width, signedness, and a conservative overflow-checked bound including the final increment. In particular an inequality bound must be reachable. Signed widening is constrained before the sign bit, avoiding a negative address index. The original scan optimization remains a two-sided code-generation gate: pass-on uses one increment, pass-off retains more. A reduced-width exhaustive proof test covers all comparison operators, both branch orientations and pre/post-increment comparisons. The rewrite also handles a store using the same pointer phi as both address and value; otherwise removing the phi would leave its value use dangling.

## Definition-based nonzero proof

An additional IR audit found that constant-cast resolution masked only the destination width, not the source width: an out-of-range constant interpreted in an 8-bit source could incorrectly be treated as a nonzero 32-bit value. The resolver now interprets each source width and signedness before conversion, handles all 128 bits, and uses a single bounded iterative traversal. The OR-definition walk is likewise iterative and examines both operands, so it cannot recursively exhaust the compiler stack and can discover a proof on either side. Unit fixtures cover source-width truncation, signed extension, high 128-bit bits, either OR operand, and adversarial depth. These are IR-level edge cases; a C-level miscompile has not been demonstrated.

## DWARF line-state correctness (not full source-variable support)

A GNU-as comparison demonstrated that the built-in assemblers silently discarded `.loc` attributes: an input specifying `is_stmt 0`, `prologue_end`, `epilogue_begin`, `basic_block`, ISA and a discriminator produced only plain rows. The old S41 compiler is retained as a red control; the new `check_dwarf_loc_options.py` rejects its x86-64 object because all attributes were missing.

The shared parser and DWARF v4 line writer now carry these six attributes through the x86-64/i686, AArch64 and RISC-V assemblers. Persistent `is_stmt`/ISA values are computed in source order before rows are split into executable sections; the writer resets each sequence to DWARF defaults and emits the needed state transitions. One-row flags and discriminators reset after their row. A multi-byte discriminator is emitted without a per-row allocation. The new test decodes row *semantics*, rather than matching raw opcode bytes, against GNU as for all four targets, including cross-section state, and validates both relocatable objects and GNU-linked images. All four legs pass in this environment; missing optional cross oracles are explicitly skipped rather than reported as passes. The existing multi-object/linker/strip/compressed-input DWARF suite and GDB line-resolution test also pass. Unit tests cover valid options and invalid/missing arguments; full exact-tree CI is still required.

This is a line-table interoperability fix, not a complete DWARF implementation. GNU `.loc view` remains unmodeled, and the earlier GDB red control for source locals/parameters and type DIEs remains unresolved; optimized variable locations, lifetimes, inlined-call scopes and type reconstruction also remain open. There is no evidence of overall quality, performance or usefulness exceeding GCC or LLVM.

## Fast-CI preprocessor regression and split terminator

The first exact-tree fast run after #1043 was stopped after a real failure: 7,074 unit tests passed, one failed, and ten were ignored. The failing upstream test `a_bridged_ordinary_line_keeps_its_break` exposed an over-conservative rebase integration guard; the earlier targeted compiler regressions did not exercise that Rust assertion. This run is not a fast-CI pass.

The guard now permits a safe break on an ordinary line that entered inside a block comment only when both the physical and splice scanners have seen the comment close, while directive context and all other safety checks still apply. A further diagnostic red control exposed a separate source-position defect when a closing `*/` itself was formed across a splice: GCC 16 diagnoses an undeclared token at line 4 column 2, while the prior LCCC reported line 2 column 10. The splice scanner now carries a pending comment-ending star across physical parts, without letting the `*` of the opening `/*` double as a terminator. The fixed compiler reports line 4 column 2, like GCC. The 32/64-bit GNU11 O0/O2 execution and diagnostic-position controls, C23, 400 seeded comment bridges across five frontends, and the four-target DWARF regressions pass. A complete Rust-unit rerun and exact-tree fast CI are still required before this is gated.
