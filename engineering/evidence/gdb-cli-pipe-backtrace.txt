=========================================================

Reproducer: 2000 `@ ;` lines (`/tmp/many-errors.c`); inferior stdout+stderr

`lccc bad.c 2>&1 | head -2` does. The reader is a Python thread so the close
is deterministic (a shell `head` can exit after the compiler already filled

Conclusion
----------
`eprintln!` -> `std::io::stdio::print_to` -> `panic_fmt` (rc=101). The first
fix only replaced 60 sites in `src/common/error.rs` and
`src/driver/pipeline.rs`; the FINAL driver verdict in `src/lib.rs:157` and 8
sites in `src/bin/lccc_ld.rs` still panicked. Fixing the class required all
1,100 CLI-text macro calls in src/. After the fix, the same reproducer exits
rc=1 with byte-identical diagnostics, and neither GDB breakpoint fires.
