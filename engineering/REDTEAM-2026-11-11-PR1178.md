# Red-team audit of PR #1178: seven red lanes, five root causes

Date: 2026-11-11. Base: `fc8350a46fc97688d10d0f12183e911ab6e7c58d` (`main`).
Subject: PR #1178 as posted, commits `9e2f97867` (the 128-bit integer series)
and `c444c8a09` (a follow-up that tried to turn CI green).

Every claim below was reproduced on the base and on the patched tree with the
commands named next to it. Where a claim could not be checked locally it says
so.

## 1. A long double copy destroyed live registers (`main`, x86-64)

`*out = *in` for an `IrType::F128` value is fused by the generic driver into
one block copy (`src/backend/generation.rs`, "Exact F128 load->store"). The
x86-64 `emit_memcpy` stages its two addresses in `%rdi` and `%rsi`. That is
correct for an IR `Memcpy`, which liveness treats as a call point. The fused
pair is two ordinary instructions to liveness, so the allocator keeps values
in `%rdi`/`%rsi` across it, and the staging overwrote them.

Reproducer, no `__int128`, no varargs, System V ABI
(`tests/regression/f128_copy_keeps_live_registers.c`):

```c
word live6(word **xpp, long double **qq, long double *out) {
    word *xp = *xpp;
    word a = xp[0], b = xp[1], c = xp[2], d = xp[3], e = xp[4], f = xp[5];
    *out = **qq;
    return a + 3 * b + 5 * c + 7 * d + 11 * e + 13 * f;   /* 183 */
}
```

`main` returns `422198348081793` at `-O1`, `-O2`, `-O3` and `-Os`; GCC, Clang
and the patched tree return 183. Five of the file's checks fail on `main`.

Why PR #1178 exposed it: a body that contains a 128-bit integer instruction
loses `%rdi`, `%rsi`, `%r8` and `%r9` for unrelated reasons
(`regalloc::x86_body_has_i128_ops`). `i128_split` removes those instructions,
the registers return to the pool, and the Microsoft-ABI variadic test, which
copies a long double while six values are live, started to crash. The split
IR of that function is correct; the defect is in the copy.

`c444c8a09` diagnosed "a 128-bit home reached through a derived address" and
restricted `i128_split` so that the wide instructions come back. That hides
the defect behind lost optimisation: the reproducer above has no 128-bit
integer in it and still fails with that commit. Its `merge_entry_allocas`
change addresses a layout the reproducer does not have (the allocas of the
crashing function are one contiguous run) and is not adopted.

Fix: a hook, `ArchCodegen::emit_f128_exact_copy`. The default forwards to
`emit_memcpy` with the type's own size, which is right wherever the inline
copy stages in reserved temporaries (AArch64 `x9`-`x13`, RISC-V `t1`-`t4`,
i686 `%eax`/`%edx`, and `%esi`/`%edi` saved around `rep movsb`). x86-64
overrides it (`emit_f128_exact_copy_impl`): each address is reached through
the pointer's own home register when it has one and through `%rcx` otherwise,
and the payload crosses in `%xmm0` (without SSE: in `%rax`, a word at a
time). Two instructions when both pointers are in registers. Nothing but
`%rcx`, `%rax` and `%xmm0` is written; a unit test enumerates every home
combination and checks exactly that.

Alternative considered: make the fused pair a liveness call point. Rejected:
every value live across a long double assignment would be evicted to a
callee-saved register or a slot to protect two registers the copy does not
need.

## 2. The same fusion copied 16 bytes for a 12-byte object (`main`, i686)

The fused copy was `emit_memcpy(dst, src, 16)` on every target. An i686
`long double` is 12 bytes, so the member behind it was overwritten:

```c
struct boxed { long double value; unsigned tail; };
void tail_survives(struct boxed *box, const long double *q) { box->value = *q; }
```

`box->tail` is clobbered on `main` at `-O0` to `-O2`. The hook's default now
copies `IrType::F128.size()` bytes. Pinned by the `_i386` variant of the
regression file (three checks fail on `main`).

## 3. Vector call results outlived the register that held them (PR #1176)

`CodegenState::call_ret_vector_in_xmm0` records values known to sit in
`%xmm0`/`%ymm0`/`%zmm0` so that `return ext8(a);` returns in place. PR #1176
inserted into the set and never emptied it.

* It was not cleared between functions. Value ids restart at 0, so a stale id
  named an unrelated value of a later function. `c_ptr` (`return *p + b;`, no
  call at all) at `-O1 -mavx2` loaded its result into `%ymm5` and returned the
  incoming argument. The CI gate ran `-O0` and `-O2` only and missed it.
* It was not cleared when the register was written. In `c_rvo` at
  `-O0 -mavx2` the call result is copied to the hidden buffer through `%xmm0`
  and the `return` then skipped the reload: the red lane.
* `emit_copy_i128_impl` also asked whether the *destination* of a copy was
  resident. With a stale id, a 128-bit integer copy stored whatever `%xmm0`
  held instead of its source.

Fix: residency ends with the function, with the block, and before every
instruction that is not a rename (`Copy`) of a resident value
(`expire_call_ret_vector_residency`, called at the head of the driver's
instruction loop, ahead of every fused and deferred path). The destination
test is gone.

Rejected alternative: clear the set in `invalidate_vec_scratch_peephole`. The
driver announces a scratch clobber before *every* `Copy`, renames included, so
the rename chain the set exists for would never be followed, and the second
insertion site (insert, then invalidate) would be dead code.

What survives: at `-O2 -mavx2` the patched output is byte-identical to the
PR's and 24 lines shorter than `main`'s for `wide_avx.c`; at `-O0` it is
byte-identical to `main`'s. `check_vector_abi_wide.sh` now also runs `-O1`.

## 4. `-g` changed the generated code (`main`)

`combined_local_pass` retires `movq %b, %a` after `movq %a, %b` when only
frame stores stand between them, and looked for the second move within
`(i + 8).min(len)` *lines*. Hidden debug rows and deleted lines are lines.
In `simd_defer_chain.c` at `-O1` three rows pushed the reverse move past line
eight, it survived, and a later fold then chose a different copy. The same
function compiled to different code with and without `-g`.

The pass was written for the code shape `main` emits; the shape this PR emits
reached the boundary. Only this pass restores equality when skipped
(138 names bisected), and `CCC_PEEPHOLE_TRACE` shows the first divergence in
its output.

Fix: the bound is on instructions. `dead_code::eliminate_dead_reg_moves` had
the same index-based window and gets the same treatment. Neither bound moved:
the unit test puts each pattern on the last instruction its window reaches,
with one and with three hidden rows per instruction, and one instruction
further.

Collateral effect measured: 1343 regression sources at their own flags and
684 at `-O1` compile to identical assembly before and after, except the three
new long double tests.

Not done: forty-odd other index-bounded scans exist in the x86 peephole
passes. The invariance gate samples one source in 32 plus 323 sentinels and
passes; that is evidence, not proof, for those.

## 5. Tests that described an earlier design (this PR)

* `test_x86_i128_narrow_and_relay.py` used two environment switches that
  became `CCC_DISABLE_PASSES` tokens, and asserted "no `movdqu`" for
  memory-to-memory copies. `*d = *s` is one `movdqu` each way, as in GCC and
  Clang. The property that matters is "no 16-byte load of a frame slot that
  8-byte stores wrote"; the module now tests that directly (`stalled_loads`,
  with its own positive and negative controls) and the kill switch is its
  negative control.
* `test_x86_i128_mul_redteam.py` required the emitter's literal register
  names in peepholed output. The peephole forwards a copy into an operand
  (`imulq %r10, %rdx`). The literal sequence is now required of the raw
  emitter output and the arithmetic of the peepholed output.
* `multiword_tests.rs`: one negative case forbade a fold the implementation
  performs by design and correctly (arithmetic on an unrelated register
  between the halves of a product). It is now a positive case checked against
  the CPU model, with real negatives beside it.
* The typeof recovery comment lacked the phrase its own test requires, and a
  debugging probe was left behind it. Both corrected.

## Measured gaps that remain

Instruction counts at `-O2`, lccc / GCC 16.2 / Clang 23.1.5:

| function | lccc | GCC | Clang |
|---|---|---|---|
| `u128 join(u64 lo, u64 hi)` | 16 | 3 | 3 |
| `u128 mul_uu(u64, u64)` | 10 | 3 | 3 |
| `u128 add3(u128, u128, u128)` | 13 | 7 | 7 |
| `u128 mac1(u64 a, u64 b, u64 c, u64 d)` = `(u128)a*b + c + d` | 30 | 10 | 8 |
| `void copyu(u128 *d, const u128 *s)` | 9 | 3 | 3 |

Two causes account for all of them.

1. A returned 128-bit value taints its whole island in `i128_split`, because
   the IR has no instruction that joins two 64-bit values into a 128-bit one.
   Storing the halves to a frame home and loading them back was measured and
   is not the answer: each half dies at its store, so it never gets a
   register and the reload cannot be forwarded (15 instructions for a
   two-`lea` function). The join has to consume both halves at once, which
   means a new IR construct with a lowering in four backends.
2. In a body that still contains a wide instruction, pointer and integer
   parameters are homed in callee-saved registers although `%r10` and `%r11`
   are free (`copyu`: `pushq %rbx; pushq %r12; ...`).

Also open: `v8 f(v8 a) { return ext8(a); }` is 12 instructions against GCC's
1 (`vector_abi/check_vector_return_abi.sh`, red on `main` and not wired into
CI); `vmovups %ymm0, %ymm0` survives in `c_rvo` at `-O2 -mavx512f` on `main`
and here.
