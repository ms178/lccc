# Red-team audit of upstream PRs #359–#362 + miscompile root cause closed

Base: upstream main `da964ed4` (Merge PR #362). Auditor: ms178-1.patch session
(rebased tree = `da964ed4` + the S26 MachInst commit, cherry-picked as
`081c8faa`). Every verdict below was verified programmatically (unit tests,
differential harnesses, and A/B builds of the exact upstream commits), not by
reading alone.

## Verdicts per PR

### PR #359 (`ab9c11a7` — peephole FP-load fold + pool-constant hoist): AGREE with goals, ONE SOUNDNESS HOLE FOUND AND FIXED

The liveness refinement (accepting a fold when the first later mention of the
loaded xmm *fully overwrites* it) is directionally correct, but
`is_pure_xmm_overwrite` classified the **reg-reg scalar moves**
(`movsd`/`movss`/`vmovsd`/`vmovss`) as full overwrites. They are MERGE writes:
they preserve the destination's remaining bits (SDM: MOVSD/MOVSS legacy and
VEX forms merge). Those preserved bits can come from the very load being
deleted — a memory-source scalar load zeroes bits above the element — so
deleting the load changed observable state:

```asm
    movapd %xmm9, %xmm11          # define xmm11 = V (V.hi != 0)
    movsd  32(%rsi), %xmm11       # deleted load: hi = 0
    vmulsd %xmm11, %xmm2, %xmm2   # consumer (fold target)
    vmovsd %xmm12, %xmm11         # "overwrite" per #359 — merges hi
    vmovapd %xmm11, %xmm5         # packed read observes hi: 0 with the
                                  # load, V.hi without it  -> MISCOMPILE
```

Proven red on the unfixed upstream code by three unit tests (both fold passes
+ single-precision variant), fixed by splitting the mov families into
scalar-merge forms (only the memory-source spelling defines the whole
register) and full-width/zero-extending forms; the VEX 3-operand self-xor
spelling (`vxorpd %r, %r, %r`, `vpxor …`) is now recognized too, un-vetoing
folds the old 2-operand-only check rejected. 6 new tests.

Two quality defects in `hoist_repeated_fp_constant_loads`, both fixed:
1. duplicate token scans of one rmw line inflated the "≥2 rewritten uses"
   threshold (sites not deduplicated) — hoisting a single-use line keeps the
   static count identical and adds a dynamic pool load;
2. the materialization hardcoded `movsd` even for single-precision-only
   symbols — an exact 4-byte `movss` pool read is now used when no
   double-precision site needs the full 8 bytes (value-safe either way; the
   narrow read is precise and documents intent).

### PR #360 (`983a635f` — flush-shadow fix, small-slot gate, size-aware layout): AGREE

* `flush_machinst()` shadow clear on the no-op early return: root-caused,
  minimal, sound (a no-op window needs no replay — values already sit at
  their destinations). The tty_io.c ICE mechanism is coherent.
* Small-slot certification gate (`lower_instruction_typed_ss`): coherent with
  the #358/#362 classifier invariant (small_slots ⊆ {v : value_types[v] ≤ 4B});
  the full-width S64 fallback is always safe given that invariant, and the
  `CCC_VERIFY_SLOT_WIDTHS` verifier from #362 cross-checks it.
* Diagnostic bisect knobs (`CCC_MI_FN_DISABLE`/`CCC_MI_FN_FORCE`/
  `CCC_MI_ALL_CLASSIC`): env-gated, no default-build behavior change;
  consistent with the repo's existing `[MI-PROFIT]` diagnostics convention.
* Size-aware block layout (RPO start for -Os/-Oz, existing order for
  -O1..-O3): measured, reversible via the enum refactor; no throughput risk.

### PR #361 (`fcab62c6` — BitTest(base, 0) folding + slot-stress harness): AGREE

`BitTest(base, index)` is `(base >> index) & 1`; the old `rhs_zero → 0` fold
was copy-pasted from the shift arms and turned `base & 1` into 0 — a real
miscompile (found by their own fuzz generator, seed 1). The fix (only a zero
BASE folds), the replaced unit tests, and the deterministic 4-way differential
harness (`gen_slot_stress.py`/`run_slot_stress.sh`) are exactly right. The
harness immediately paid for itself twice (see below).

### PR #362 (`c8683317` — fixed-point value type map, hull-model coloring, Tier-2 on): AGREE, with one important correction to its claim

* The widening-fixpoint `compute_value_type_map` (widest def wins, ParamRef
  seeded up-front, phi back-edges reach the wide type) is the correct
  single-source-of-truth hardening of #358's width veto.
* Making hull (fat-interval) interference the DEFAULT and per-segment sharing
  an A/B-only opt-in is MORE conservative than the earlier audit doc's plan
  (per-segment default + conservative fallbacks) and matches the register
  allocator's own model (`LivenessResult::intervals`), so a shared slot is
  only ever granted to values whose complete live ranges are disjoint. The
  closed-boundary rule (touching points interfere) correctly models hidden
  accumulator stores at a boundary point. AGREE.
* **Correction**: the commit message attributes the preboot-ZSTD corruption
  solely to a width bug and declares the coloring never a trigger. The width
  analysis is right, but "the defect is in the layout, not in any
  optimization" is now proven incomplete — see below: the OTHER pre-existing
  -O2 miscompile they documented (BUG-2026-09-03) was NOT in the layout at
  all; it was a codegen emitter width bug that survived all four of their
  "fully conservative" layout configurations precisely because it is
  layout-independent.

## The noted miscompile — root cause found and closed

`engineering/BUG-2026-09-03-O2-vla-store-miscompile.md` (repro
`tests/bugs/o2_vla_fill.c`, slot-stress seed 32) documented -O2/-O3 wrong
results in all four layout configurations. A/B builds of the exact upstream
commits isolate the trigger:

| tree | -O2 result | verdict |
|---|---|---|
| `4762fea1` (#361) | does not even build (`-D warnings`: the dead wildcard arm my upstream-repair had removed — subsumed by #362's rewrite) | — |
| `c8683317` (#362) | `12877992986365140340` / seed32 `13301157349257968134` — both WRONG | bug present |
| rebased tree (#362 + S26 MachInst commit) | `12878068022990762980` / seed32 `10994965426039773268` — both match gcc | bug FIXED |

Root cause (from the -O2 assembly diff, not from instrumented guessing): the
unrolled init body stores `b[3] = 3041712681u` — a 32-bit constant OUTSIDE the
signed imm32 window — by staging `movabsq $3041712681, %rax` and then storing
the stage register with the wide-imm memory relay's **default S64 width**
(`movq %rax, 12(%rbpVLA)`), writing 4 bytes past the 16-byte VLA. On the
stack-layout ordering (b allocated directly below a), those 4 bytes are
exactly **a[0]'s low half**, which the earlier a[0] store had defined. The
reduce chain `g = g*33 + (a[i]+b[i])` amplifies the lost 32 bits by 33³:
`75045033622640 / 33³ = 2.088e9` — precisely a[0]'s erased low half. The same
defect class (wide-imm memory relay ignoring the operand size) was already
caught on the FLOAT path by the S26 suite regression (`fp_arith` NaN store,
exit 139) and hardened there ("the Mov emitter's wide-imm memory relay now
honors the operand size — `movl %eax` for S32"); the integer path needed no
new fix in the rebased tree because the hardening is on the shared relay.

Why the bug doc's bisection stalled: the four "fully conservative" layout
configurations cannot mask it because the corruption is an over-wide STORE,
not a slot-sharing collision — #358's slot-width veto sizes SLOTS from the
emitter width, but the VLA frame region is a dynamic alloca, and the store
itself is wrong-width regardless of slot width. Likewise no IR pass knob can
mask it: the wrong instruction is emitted by the backend relay for IR the
-O2 unroller produces (straight-line wide-constant stores into VLA slots).

Actions taken:
1. The bug is fixed on the rebased tree (verified at -O0..-Os and -O3, both
   repros, plus the full 4-way stress matrix below).
2. `tests/regression/vla_narrow_const_store_family.c` added — pins the class
   at every VLA-tail boundary and width mix (64-bit wide const, >2³¹−1 const,
   narrow const). Verified to FAIL on `c8683317` and PASS on the rebased
   tree, so the gate cannot silently rot.
3. `run_slot_stress.sh` default range extended 1..20 → 1..45 as the bug doc
   recommended: verified 720/720 (seeds 1..20 = 320/320, seeds 21..45 =
   400/400, -O1/-O2/-O3/-Os × 4 layout configurations), including seed 32.
4. The BUG doc's "recommend next steps" items 1–3 are thereby closed; item 3's
   instruction to keep the failing cases out of tests/regression lapses with
   the fix.
