## Bounded signed IV experiment

A same-type arithmetic right shift by a valid constant proves a strict upper
bound on its result even if the shift input arose from wrapping addition. Use
that bound for unit-stride signed trajectories; do not infer that the input
addition cannot wrap. Keep seed, dominance, loop topology, guard polarity,
inclusive-predicate, and full member-closure obligations. Negative seeds,
maximal exposed seeds, larger steps, inclusive runtime predicates and invalid
shift counts remain rejection cases. The boundary C witness masks all accesses
and caps iterations; it includes INT_MIN/INT_MAX and a deliberately wrapping
`n + 1`. Tests and measured benefit were pending when this section was written.

A deeper review rejected my own assumption that a correctly rounded binary128
carrier is sufficient for x87 literals. A literal just above an x87 midpoint
loses its distant sticky bit when rounded to binary128 first, then wrongly
rounds down to x87. GCC and Clang emit mantissa 8000000000000001 / exponent3fff;
S49 emits 8000000000000000 /3fff. The expanded generated-literal oracle
independently rejects S49 at case425, while GCC/Clang agree on every case.

For hexadecimal L literals, round directly to the target precision first:
64 significant bits for x87, 113 for AArch64/RISC-V long double. Widening the
precision-64 result into the existing binary128 token carrier is then exact:
both formats use the same exponent bias, and a 49-bit shift preserves normal,
subnormal, infinity and signed-zero encodings. Explicit Q literals retain full
binary128 precision regardless of the long-double target. The f64 convenience
approximation is derived from the rounded carrier, not the original unrounded
text. The driver establishes the thread-local target before lexing; tests check
both settings and restore them even on panic. This avoids adding a second
literal payload throughout the AST/IR and avoids relying on host long-double
arithmetic. Decimal-to-x87 rounding is not claimed fixed by this hex-specific
change.

Main was refreshed to `84a62201cc90a41c9a0eefe2faf5196f43370cfa` (PR837).
The validated S52 patch/source/bundle were hash-checked before recovering exact
history and rebasing. Upstream's vector-copy liveness refresh and call-argument
observability fixes remain intact. The TempFile conflict keeps fallible,
fail-closed reservations and retained pending-path ownership from our branch;
all six upstream lifecycle tests were retained alongside our six tests.

### Architectural defect and implementation decision

`MOVSD m64,xmm` zeros bits 127:64; `MOVSS m32,xmm` zeros bits 127:32.
Legacy register-register scalar moves merge those bits instead. VEX memory
loads clear everything above the loaded scalar. The old forwarding table
confused these forms, removed observable same-register zeroing, used the wrong
low-lane source in a VEX merge, and could emit nonexistent SSE2 XMM-to-XMM MOVD.
The GP relay optimization independently substituted merging MOVSD for zeroing
MOVQ, while generic self-move classification wrongly discarded XMM MOVQ.

* Forward 64-bit scalar loads with MOVQ/VMOVQ, retaining each load's encoding
  family and exact architectural zeros. No old-destination dependency remains.
* Forward 32-bit VEX loads with AVX VINSERTPS immediate 14: select source lane
  zero and zero the other three lanes. AVX is already required by that load;
  no AVX-512 instruction or undeclared ISA is introduced.
* A legacy 32-bit XMM source has no single-instruction SSE2 equivalent. Keep
  the memory load unless the existing proven relay fusion applies. Introducing
  SSE4.1 unconditionally or clobbering a scratch GPR would be incorrect.
* GP-backed loads use the exact-width MOVD/MOVQ conversion, preserving the
  original legacy/VEX behavior. Refresh both liveness oracles after changed
  reads so later transformations cannot use stale backing-register facts.
* Preserve GP identities, but never classify a zeroing XMM MOVQ as a no-op.
  XMM→GP→XMM relays collapse to MOVQ, not MOVSD.

Instruction definitions checked against
https://www.felixcloutier.com/x86/movsd ,
https://www.felixcloutier.com/x86/movss and
https://www.felixcloutier.com/x86/insertps ; native execution is the decisive
oracle, including a separate unoptimized original-assembly control.

### Executed correctness and performance

failed assembly on XMM-to-XMM MOVD. An unmodified legacy MOVSD result extracted
from that failed output separately compiled and failed **192/192** native

The corrected fixture executes **6,720 comparisons per stage**: original,

all FTZ/DAZ combinations and sticky status preservation. All three executables
also pass Memcheck. The entire library suite passed **4,812 tests, 9 ignored**.
No exception-relaxing or fast-math flag is used to justify the bit transfers.

Nine randomized pinned before/after rounds, using the existing verified

## S53/S54 inliner, frame-address and measurement-protocol work

### Real-zstd attribution (Callgrind, instruction level)

Function-level and per-instruction Callgrind of the real 1.5.7 library against
GCC16.2 located the deficits: the compression encode loop called outlined
`FSE_encodeSymbol`/`BIT_addBits`/`BIT_flushBits`; the fast match finder called
an outlined `ZSTD_match4Found_cmov`; the doubleFast and decode loops spend
47-49% of executed instructions on stack operands; decompression additionally
reloaded spilled copies of `&seqState.stateXX` before every FSE-state access.

### Changes, each with a negative control

* **Devirtualization before inlining.** An indirect call whose pointer resolves
  through uniquely-defined Copy values to one `GlobalAddr` of a non-weak,
  non-variadic, unlabelled definition with exactly matching scalar ABI becomes
  a direct call. The backend already emitted `call f`; the IR call graph hid
  `f` from the inliner. Reassigned pointers, ABI mismatches, weak/variadic/
  asm-labelled/declared targets and data addresses stay indirect (unit tests).
* **Joint ordinary/always_inline fixpoint.** A raw mandatory template inlined
  by the second pass could expose calls that ordinary rounds always accept;
  they survived because ordinary rounds had already ended. The rounds and
  second-pass budget are shared, so no new growth bound is introduced.
* **Bottom-up snapshot refresh.** After processing a function, later callers
  clone its processed body only when it passes the same eligibility rules
  (invocation-entry call graph) and cloning cannot duplicate grown work: a
  single-call-site static whose holder is itself never cloned, or a body
  that did not grow. Refreshing grown multi-site helpers was tried and
  rejected: unsimplified expansions pushed hot helpers out of their size class
  (zstd hash helpers re-outlined).
* **Devirtualized per-iteration hot leaf.** A devirtualized small loop-free
  static target whose call block dominates every latch bypasses caller-size
  caps, charged to the normal budget and then a relative budget equal to the
  caller's entry size. `tests/regression/inline_devirt_hot_leaf.c` +
  `check_inline_devirt_hot_leaf.py`: the pre-change compiler leaves
  `call pred_a/pred_b`; the gate requires none and GCC-identical output.
* **Rejected generalization (measured, documented):** extending the hot-leaf
  bypass to ordinary direct calls (static-inline or plain static, ≤64 IR
  instructions, in any loop or per-iteration block) won 10-15% at level 1 but
  slowed mozilla/sao level-3 compression by 21-28% (paired, 30-iteration
  batches). Bisection by object substitution isolated `zstd_double_fast.o`;
  `CCC_INLINE_SKIP` isolated two direct hash-helper clones (~9% each). The
  slower build has identical frames, ±1% Callgrind Ir, identical stack-load/
  store counts and branch mispredictions, and the effect survives stack-base
  shifts (env padding), `-falign-functions=64`, `-falign-jumps=16` and
  `-fno-align-loops`. Without a PMU the cause is unknown, so the bypass is
  restricted to devirtualized template predicates. Kill switches for A/B:
  `CCC_NO_INLINE_DEVIRT`, `CCC_NO_INLINE_SNAPSHOT_REFRESH`,
  `CCC_NO_INLINE_JOINT_FIXPOINT`, `CCC_NO_INLINE_HOT_LEAF`.
* **Constant-offset frame addresses are direct operands.** A single-definition
  `GEP(alloca, const)` resolved through GEP/Copy links to an ordinary,
  non-over-aligned, slotted alloca is addressed as `OFF(%rsp)` by every memory
  operand on x86-64, while its producer still runs for non-memory uses
  (`CCC_NO_FRAME_GEP_DIRECT` disables). `check_frame_gep_direct.py`: the
  pre-change compiler emits eight reload-then-dereference pairs in an
  eight-state FSE-like decoder; the gate requires zero and GCC output.
* **Benchmark protocol represents production.** The batched native harness
  compiled `-S` and then assembled. LCCC's integrated assembler resolves exact-
  span tight-loop alignment only for direct `-c` compiles, so every previous
  native screen measured a layout users never get. `--object-mode direct` is
  now the default (assembly is still saved; `assembly` replays history).
  Example: main's expat_xml_scan advantage (0.757 of this branch) came from a
  16-byte shift of an unaligned 19-byte inner loop crossing a 64-byte line.

### Validation and measured results

All 4,816 library tests (10 ignored; the AVX-512 masked-load native fixture
runs explicitly and passes on this host) and 944/944 regression-corpus

### Highest-value remaining work (evidence-ranked)

### Defects fixed (each reproduced before the fix)

1. One psABI classifier (`src/common/sysv_classify.rs`) and one lowering
   view of it (`src/ir/lowering/aggregate_abi.rs`). Signatures, parameters,
   call arguments, indirect calls and `va_arg` all use it, instead of the
   former size-based and layout-only guesses. X87-class returns
   (`struct { long double }`) use `%st(0)`. One-XMM `[Sse, SseUp]`
   arguments use `StructXmmReg` (the operand is an address); `F128SseReg`
   now means scalar `_Float128`/`_Decimal128` only.
2. "Is this call result packed register data or an address?" was guessed in
   three places, each differently: `expr_produces_packed_struct_data`,
   `rhs_is_small_vector_call`, and `get_struct_base_addr`. All three now ask
   `call_result_is_packed`, which reads the callee's return ABI (sret,
   two-register, one-XMM, x87). The unseeded-intrinsic size rule (the
   clmul256 regression) moved into that helper. Effects:
   - a ≤8-byte vector call result passed as an argument no longer
     segfaults;
   - `return f();` of an X87 aggregate no longer `fldt`s the bits of a
     pointer.
3. The x86 MachInst typed-call fast path (`try_lower_call_typed`, upstream
   4ef1be6cd) admitted any integer-width return and read `%rax`. An `[Sse]`
   aggregate (`struct { float x, y; }`, an 8-byte FP vector) comes back in
   `%xmm0`, so every call to a scalar-parameter function returning one read
   garbage. On main this was latent, because main returned such aggregates
   in `%rax` on both sides (self-consistent, but GCC-incompatible). The
   correct classification made it live; the gate now admits only all-INTEGER
   register returns.
4. Conditionals:
   - aggregate-typed `?:` now includes GNU vectors when deciding to
     normalise packed and address arms;
   - the address arm is loaded at the object's width (no 8-byte read of a
     4-byte object);
   - when both arms are addresses, the merge is a pointer, not `F128`
     (X87 call result versus lvalue).
5. Vector initializers: see c81a7c0bc. Array-of-vector members are filled
   per element by a shared writer on the static, compound and automatic
   paths. The object's type, never the base specifier, selects the vector
   paths: `T *p = { &v }` and `T (*fp)(int) = f` had been lowered as vector
   initializers.
6. `F128SseReg` arguments and `_Float128` returns had silent fallbacks:
   - a value without a slot became `pxor` (zero);
   - a `LongDouble` constant was narrowed to x87 bytes;
   - any other operand was dereferenced.

   One helper (`emit_f128_sse_operand_to_xmm`) now handles exactly slot
   values, `Zero` and `I128`, and raises an ICE for anything else.
   `_Float128` and `_Decimal128` literal arguments and returns match GCC
   byte for byte at -O0 and -O2.

### Harness hardening (red-team of our own gates)

- The SysV fuzzer covered only aggregate-parameter signatures, so it could
  not see defect 3. It now also checks per shape:
  - `get_K(int)` consumed as an argument, through an initializer and
    through an assignment;
  - three `?:` forms mixing a call result with an lvalue, both selections.
- **Negative control:** with the defect-3 gate removed, the fuzzer fails 9
  shape-legs (`C_ff`, `C_cf`, `C_v8c`, `U58`, …), exactly in the new forms.
- Both Python ABI gates enforce the GCC 16 oracle policy of
  `tests/regression/lib/gcc_oracle.sh`: a missing or different GCC fails
  with rc 2 and is never substituted.
- The forms matrix line-buffers its output, so a crash reports the forms
  that ran before it.
- New gates are registered fast in `ci_local.sh` and `ci.yml`:
  `sysv-aggregate-abi`, `vector-arg-forms`, `vector-static-init`, and
  `void-declarators` (left unregistered since s64).

### #848 verdict (ext_vector_type, 32675f1df)

#848 also moves 8-byte single-SSE vectors from `%rax` to `%xmm0`, and that
part agrees with GCC. Its model is Clang's (`ext_vector_type` padding), and
its CI is red (Clippy, relocation contracts). The classifier here is
GCC-exact and gated against GCC on 186 shapes and 1008 operand forms, so the
overlapping ABI part of #848 is superseded. Its `ExtVectorLayout` work is
orthogonal and still needs its own audit.

### Open (not fixed here; measured or located)

- `packed_store_type` rounds 3- and 5–7-byte aggregates up to 4 and 8
  bytes. The packed spill writes the rounded width into an alloca of the
  exact size. Check the backend's slot rounding before calling it safe.
- X87-class aggregate return code quality. For
  `struct L { long double v; }; struct L get(int k) { struct L r = { k + 0.5f }; return r; }`
  at -O2, GCC 16.2 emits 6 instructions (`cvtsi2ssl; addss; movss; flds; ret`).
  lccc emits 24, with the same result. The extra code:
  - a dead `fstpl (%rsp); popq %rax`, which is a leftover `%rax` copy;
  - three `fstpt`/`fldt` round trips through the frame;
  - a dead `movq $0` store;
  - an unneeded `%rbx` save.

  This is not specific to aggregates. The scalar
  `long double g(int k) { long double r = k + 0.5f; return r; }` emits the
  identical chain (21 instructions), so the cost is in the backend's generic
  x87 value handling: every F128 value also gets an f64 copy in `%rax`.
  This series does not touch that code. It is a missed optimisation, not a
  correctness issue.
- `LCCC_DBG_STORE` (`[DBGSTORE]` in `x86/codegen/memory.rs`, upstream
  59aeb94df) is an env-gated debug print missing from `RULES.md`'s
  debug-knob list.
- 32-byte AVX vectors: AUD-VABI-2 — fixed (one `%ymm`/`%zmm` under the AVX
  ABI level; `check_vector_abi_wide.sh` is an agreement gate now, see
  FOLLOWUP-2026-10-17-ext-vector-grid.md).
