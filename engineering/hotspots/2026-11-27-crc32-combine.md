# Hotspot: zlib-ng CRC composition — measured scope before optimization

## Identity

- Workload: `tests/benchmark/programs/zlib_ng_crc32_combine.c`.
- Upstream: zlib-ng 2.3.3, commit
  `12731092979c6d07f42da27da673a9f6c7b13586`; file hashes/license/extraction
  boundary are in `tests/benchmark/WORKLOAD_PROVENANCE.md`.
- LCCC baseline: `7604253fa62bbce385b740ea33d7ce573f21cf5a`, built with
  `fastbuild`, Rust optimization level 1, explicit two Cargo jobs and active swap.
- Functions: `zng_crc32_combine`, `x2nmodp`, `multmodp`.
- Program semantics: CRC concatenation using polynomial arithmetic, not
  byte-stream CRC throughput or complete zlib-ng compression.
- Measurement host: two-vCPU Xeon VM, not the target i7-14700KF.

## Correctness barrier

The executable checks `CRC("123456789")`, all 257 splits of a deterministic
256-byte buffer, and 320 basis/length combinations against an independently
written 32x32 linear-map reference, including lengths beyond 32 bits and
`INT64_MAX`. The multiplier's first operand is a nonzero polynomial power;
negative lengths are not supplied. Native x86-64/i686 differential tests,
source sanitizers, native ICX 2026.2.1 and remote ICC Classic all pass the
bounded checksum. No floating-point reassociation or undefined signed overflow
is used as a performance lever.

## What the machine code and measurements actually say

Static operator-body instruction counts at `-O2 -march=x86-64-v3`:
LCCC 55, GCC 16.2 55, Clang 23.1.6 59, ICX 2026.2.1 56. These are **not a
ranking**: LCCC has an outlined helper call; the other three inline it.
The repaired survey refuses to rank that scope mismatch. Raw assembly and
compiler identities are retained in the native-codegen JSON.

The default-size, 21-round, CPU-pinned experiment (262,144 passes) reports:

| Comparison | Median paired time ratio |
|---|---:|
| LCCC / GCC | 0.99924 |
| Clang / GCC | 0.81687 |
| ICX / GCC | 0.80837 |
| LCCC / best measured native oracle (ICX) | **1.23078** |

LCCC/GCC's exploratory interval includes parity. This says nothing about native
ICC performance: ICC was only available through a remote executor.

Callgrind summary instruction counts are 1,173,263,475 / 953,170,576
(LCCC/GCC). Cachegrind gives 1,173,262,927 / 953,170,028: the **same exact
220,092,899-instruction delta**. Instruction count does not predict elapsed time
by itself: the native LCCC/GCC ratio is near one despite this work difference.
No cycles/IPC or physical branch/cache explanation is asserted without a PMU.

Callgrind attribution identifies `multmodp` as dominant in LCCC; GCC's work is
inside the operator. Its per-function cost-record totals and summary do not
agree exactly, so their percentages must not be mixed. Raw profiles and both
accounting headers are preserved.

## Scope trap found by scaling the workload

At bounded `PASSES=128`, whole-entry LCCC/GCC timing was **7.8426**, dominated by
validation/reference work, while the default-size operator-heavy run is near
parity with GCC. The bounded result remains in the evidence; it is not silently
replaced or called a kernel speedup/regression. The analogous bounded Adler
screen is also reference-heavy. Always inspect which work is being measured.

## Inlining hypothesis and controlled spike

Actual `CCC_INLINE_DEBUG` output:

```text
multmodp skipped: blocks=13, inst_count=35, has_loops=true, direct_calls=3
x2nmodp candidate: blocks=6, inst_count=26, direct_calls=1
Inlined x2nmodp into zng_crc32_combine
multmodp candidate: blocks=8, inst_count=33, direct_calls=4
Inlined multmodp into zng_crc32_combine
```

The early shape exceeds the tiny-loop block bound and the larger tier's call
count; later simplification admits a candidate, but a hot helper call remains.
This is a phase/site interaction, not sufficient proof of which single cap to
change. Existing `inline.rs` records real regressions from broader relaxations.

A **source-only** `always_inline` hint on `multmodp`, with the same LCCC binary,
passes the algorithmic checks and 15 interleaved runs. Median wall time falls
from 116.204 ms to 113.177 ms (2.60%), with 14/15 paired wins. This includes
process startup and differs from the calibrated entry protocol above; do not
mix their absolute times. The full edit and raw records are retained.

**Decision: do not ship a global heuristic change from this one hint.** The
small gain does not explain the complete ICX gap, and a wider caller/loop cap
has known code-size/pressure costs. The delivered patch keeps this as a
measured research candidate, not an advertised compiler optimization.

## Next admission test

Instrument the remaining call-site rejection reason; test a narrowly scoped
loop/site cost model, capture caller frame/spills and code size, and compare
held-out gzip/zlib-ng/Expat/SQLite workloads. Inspect the generated dependency
and branch structure against current ICX, then verify any scheduling/IPC claim
on Raptor Lake with real counters and P-core affinity. Do not special-case a
benchmark name, infer callee work from caller size, or infer CPU throughput from
IR instruction count.
