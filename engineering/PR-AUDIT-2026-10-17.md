### PR #847 — driver option contracts, freestanding/builtin behavior, vectorizer control

- **Head:** `cbf72a16a34073906dcb10161027f9f860a99873`; 27 files, +4,679/−3,404 by PR metadata. GitHub reports 14 successful checks and the named candidate semantic/performance audit skipped. GitHub currently marks it **CONFLICTING** against main. `git merge-tree` finds conflicts in `src/driver/cli.rs`, `src/frontend/sema/analysis.rs`, and `engineering/archive/BACKLOG-2026-10-16.md`.
- **Worth salvaging:** the `-fno-tree-vectorize` implementation is a real missing contract on main (main currently warns for unsupported options and does not disable those automatic vectorizers); the driver’s explicit option classification removes silent fallbacks; and blanket `-fno-builtin`/`-ffreestanding` must suppress ordinary hosted-library folds throughout sema, IR lowering, math simplification, and purity inference. The explicit propagation instead of ambient thread-local state is the better design. The PR also fixes embedded-NUL `strlen` folding. GCC 12.2 locally confirms the behavior: hosted `strlen("ab\0cd")` folds to 2; under `-fno-builtin`/`-ffreestanding`, the ordinary call remains, while explicit `__builtin_strlen` still folds to 2; `__STDC_HOSTED__` follows last hosted/freestanding option. This is GCC 12 evidence, not GCC 16 validation. On this branch I also fixed the narrow embedded-NUL length defect in both the front-end constant evaluator and post-inline IR `strlen` folding through one shared helper, with a unit regression for `"ab\\0cd"` and a plain-string positive control. The two focused Rust test groups have now run (2 enum-scope and 2 string-length tests passed each); the end-to-end embedded-NUL contract also passed with GCC 16.2 at `-O0`/`-O2`, including the `-O2` no-`strlen`-call assertion.
- **Red-team caveat:** the PR threads a blanket `no_builtins: bool` and refuses `-fno-builtin-<name>`. Main already has a per-name `BuiltinPolicy` for libcall synthesis. The best integration should either explicitly refuse per-name options until their entire fold path is wired, or preferably thread the existing policy object through sema/IR/pass consumers so `-fno-builtin-strlen` suppresses every relevant fold without losing supported per-name behavior. Do not merge the boolean alongside the policy and leave two sources of truth. Preserve main’s historical backlog archive; do not accept the PR’s stale documentation replacement as current history.
- **Verdict:** high-value changes, but rebase/resolve the two source conflicts deliberately, preserve archival records, and add tests for per-name-vs-blanket interactions. Do not cherry-pick the PR wholesale or claim performance gains; its benchmark lane is a regression gate, not a measured speedup.

### PR #849 — `ext_vector_type` padded layout and by-value ABI (merged in current main)

- **Merged head:** `af33aaeaae5598fc7ffbf08df77d37ac1de8bf06`; 58 files, +3,539/−792; merge commit `5eb1e4f1d1ab7b8720cb22251c8e9ebbbbf0b1da` on 2026-10-17. Final hosted rollup is green: all 14 named checks succeeded, including assembler/linker, complete benchmark corpus, and aggregate Test Suite. Gate parity on the feature branch passed (264 commands, 25 invocation contracts, 2 asm-diff gates). This is now part of the baseline, not an open candidate.
- **What improved relative to #848:** the hardening revision changed `vector_temp_needs_zero_init` and reported reducing the copy count from 48 to 42 against a ratchet of 44. Unlike #848, the final #849 assembler/linker lane and aggregate Test Suite passed, so the exact #849 gate—not just its self-description—cleared. Keep the old 48>44 failure scoped to #848.
- **Design assessment:** the first-class `CType::ExtVector` / `ExtVectorLayout` separation from GCC `vector_size` is the right abstraction boundary. Logical lane count, padded storage size, alignment, element storage, and bool packing are explicit properties rather than inferred from a byte count. The shared array-of-vector initializer planner and runtime/layout tests are directionally sound. The merge is substantial (+3.5K/−0.8K across type representation, front end, IR lowering, x86 back ends, and ABI classification); the final CI receipt is meaningful correctness/gate evidence, but not proof of all cross-compiler ABI shapes or runtime speedup.
- **Unclosed ABI contract:** the cross-ABI script documents and excludes mixed Clang/LCCC `f64x1` legs because Clang/GCC use MEMORY while LCCC uses `%xmm0`; i386 `f32x2` carrier differences are also excluded, and some Clang self-inconsistent i386 cases are skipped. The workflow does not set `LCCC_REQUIRE_CLANG=1` in the visible invocations, while the script explicitly permits skipping the Clang oracle when missing. No local Clang was installed in this harness. Therefore the green PR does **not** prove full Clang interoperation for those shapes. Pin/provision the documented Clang version, fail closed if absent, and either implement mixed `f64x1`/i386 shapes or explicitly narrow the promised ABI contract.
- **Architecture red-team:** i686 ext-vector stack-lane signaling is encoded as the exact `[EightbyteClass::NoClass]` sequence with `struct_size == None`, reusing a SysV x86-64 classification enum as an implicit i686 control tag. This is a non-local, fragile invariant; prefer an explicit target-specific `ArgInfo`/carrier variant. No collision is claimed today; this is a maintainability/proof-boundary concern, not a demonstrated miscompile.
- **Current-main status:** PR #849 is merged and passed all 14 hosted checks. The documented Clang/i386 exclusions still bound what that green result proves; the i686 sentinel merits a follow-up review. The vector-copy ratchet is a static instruction-count contract, not controlled runtime A/B evidence. Track ABI exclusions as explicit limitations/follow-up, not as pending salvage or as a performance claim.

### PR #848 — historical `ext_vector_type` head, now closed unmerged

- **Historical exact head:** `2285e0d59576599038179ae8594d8d55f9f8a5e7`; GitHub PR metadata records 54 changed files, +3,787/−540. GitHub closed it unmerged on 2026-10-17; its successor is #849. - **High-value design intent — agree:** keeping Clang `ext_vector_type(N)` distinct from GCC `vector_size(bytes)` is the right type-system boundary. A first-class descriptor separating logical lanes from padded object storage/alignment and bool bit-packing is materially safer than inferring lanes from byte count. A shared initializer planner for arrays of ext-vector leaves is a defensible centralization point. Layout, global-object, and mixed-compiler by-value tests are the right categories, and current main now represents these distinctions through the model merged by #849.
- **Do not accept this historical head wholesale — direct red-team evidence:** the exact-head hosted run (39037128336) marks the normal and debug regression corpora failed because `vec_incdec_elementwise` compiles but aborts at runtime (`rc=-6`); the SSA run reports the same regression. This contradicts the PR's own latest fix claim that `vector_size` codegen is preserved. Separately, the assembler/linker annotation reports **48** runtime-kernel vector copies against the newly lowered budget of **44**. I independently built the PR source at `ce7a8ec` (compiler code unchanged by the subsequent CI-only annotation commit) and reran `check_vector_copy_elimination.sh` with GCC 16.2: it likewise reports 48 > 44 (46 checks pass, one fails). This is not permission to raise the threshold; the claimed measured 42 is not reproduced and the intended code-quality improvement must be explained and demonstrated before accepting the ratchet change.
- **ABI evidence and remaining gap:** latest hosted Frontend/ABI is green. Locally, with the PR-built compiler, LCCC→LCCC ABI runtime cases passed for m64 and m32 at O0/O1/O2; its two gates' layout/runtime and emitted object-size/alignment tests passed for both widths. Local Clang was unavailable, so local cross-compiler cases were skipped; hosted CI is the evidence for those mixed legs. However `check_ext_vector_abi.sh` deliberately excludes all mixed-compiler `f64x1` cases: its own comments say Clang passes/returns that type in MEMORY while LCCC uses `%xmm0`. That is a known interop mismatch, not proof of a Clang oracle defect. Since this feature promises Clang extension ABI compatibility, do not count the same-compiler legs as closure of this shape; implement the Clang carrier or explicitly narrow the documented support contract. The script also makes Clang and i686 availability optional unless environment variables are set; hosted wiring should force both prerequisites rather than permit silent skips.
- **Architecture/design cautions:** the i686 path overloads SysV `EightbyteClass::NoClass` as a sentinel for stack-passed scalarized ext-vector lanes and reuses INTEGER-class arrays to identify i686 multi-GP return bundles. This couples i686 mechanics to a different ABI's classification vocabulary. Prefer an explicit target-neutral/target-specific ABI carrier enum or lane-passing descriptor, and prove ordinary scalars/aggregates can never collide with the sentinel. Review all fixed/variadic, direct/indirect, return/call, optimization-level, and 1–4-lane/packed-bool cases before treating the marker plumbing as complete.
- **Verdict:** #848's exact-head failures remain valid historical evidence, but its successor #849 fixed the reported vector-size runtime failure and copy-count gate, passed all hosted checks, and is now in current main. Preserve the old 48-vs-44 receipt as an #848-only result. The merged design still has the explicitly documented mixed-ABI exclusions above; do not convert green CI into a claim of full Clang interoperability or runtime performance superiority.
