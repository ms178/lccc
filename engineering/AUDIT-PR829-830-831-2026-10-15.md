### RISC-V review decision for #829

The correction to the shared GOT relocation number is directionally important: the PR notes that the current `R_RISCV_GLOB_DAT = 6` value aliases `R_RISCV_TLS_DTPMOD32` in the RISC-V psABI, and uses symbol-based `R_RISCV_64` relocations for covered preemptible GOT/data-pointer cases. But the 216-case matrix does not cover `R_RISCV_32`. The current `R_RISCV_32` path computes and writes `S + A` directly, so a shared-object/preemption claim needs a case that distinguishes a link-time absolute value from a loader-resolved symbol value. Add that case across local, default-visible/preemptible, hidden/protected, undefined, and absolute-symbol combinations, then run the 13 loader/interposition cases under the target loader. Also review unresolved strong `STV_PROTECTED` handling. Without those proofs and a clean rebase, carrying the entire 436-file PR into #831 would multiply risk rather than improve this patch.

## High-confidence changes made in this working tree

### FXRSTOR liveness

`FpLiveness` previously modeled state-save reads but did not model definite state-image restore writes. Consequently, a legacy `movaps %xmm6, %xmm7` could appear live across `fxrstor` when the restored XMM7 value was read later, preventing a safe dead-move elimination. The new effect transfer treats `fxrstor`, `fxrstor64`, and `fxrstorq` as writes to low XMM0–15 only. It leaves YMM/ZMM upper regions live and deliberately does not kill anything for XRSTOR/XRSTORS, whose actual component writes depend on runtime masks and state-bitmap conditions.

Added tests exercise all three FXSAVE-format spellings, assert the legacy move is actually removed by `eliminate_dead_fp_moves`, assert a VEX/YMM move with live upper state is retained, and assert XRSTOR-family operations do not unconditionally kill masked state. These Rust tests are pending a Rust-enabled CI run; they were not locally compiled here.

### Failure diagnostics

The frontend GCC16/i686 provisioning step now captures and prints its full install log and emits an Actions error annotation with the last useful lines on failure. The strict linker runner emits an Actions annotation for each failure (and strict warning/skip), including the case name and detail. These changes improve diagnosability; they do not claim to fix the underlying provisioning or linker failure, and have not yet been exercised by a hosted run.
