## Qualifiers in `CType`

`CType` had no qualifiers, so lccc accepted conversions C forbids and never
warned about a dropped qualifier. gcc-16 measurements before this series:
`int **pp = cpp` (`const int **`) and `const int **q = ipp` were accepted
(gcc: errors, C11 6.5.16.1p1 allows adding a qualifier only at the first
level), and `int *p = cip` was silent (gcc: `-Wdiscarded-qualifiers`).

**Representation.** `CType::Pointer(Box<CType>, PtrQuals)` with
`PtrQuals { space, cvr }`. `cvr` holds the pointee's const/volatile/restrict.
Equality and hashing compare the address space only, so every existing
`==` keeps meaning type identity up to qualification, and code that does not
care about qualifiers did not change. The parser's `CVR_*` star bits alias
`PtrQuals`' bits.

**Recording, and the rule that keeps it sound.** Qualifiers are recorded
where the declaration states them: declarator stars (including stars inside
parentheses, `int *(* const p)`), typedefs (`typedef char *const T`), type
names in casts and `sizeof`, struct members, parameters, and the composite
of `?:` (the union of both arms' qualifiers, C11 6.5.15p6). A position lccc
cannot attribute exactly is recorded as unknown, which makes every check
silent there rather than wrong: lccc never claims more qualifiers than the
source has. `_Atomic` is not modeled and never diagnosed.

**An lvalue's own qualifiers.** `&x` has type pointer-to-(type of `x`), so
the result's pointee qualifiers are `x`'s own: for a member, the outer
object's qualifiers plus the member's (`&cs.m`, `cps->m`, anonymous members,
union members); for a pointer object, its last star's (`int *const p` ->
`&p` is `int *const *`); for an array parameter, the qualifiers inside its
first `[...]` (C23 6.7.7.4p7: `int a[const 2]` is `int *const a`).

**Diagnostics, all byte-identical to gcc-16 (line, column, text, option):**
`discards '<q>' qualifier from pointer target type [-Wdiscarded-qualifiers]`
in initialization, assignment, return and argument passing;
`[-Wdiscarded-array-qualifiers]`; the multi-level
`[-Wincompatible-pointer-types]` errors; `?:` pointer type mismatch,
pointer/integer mismatch and type mismatch; `comparison of distinct pointer
types lacks a cast` (C23 6.2.7 compatibility of the unqualified pointees,
see the `3188d03cd` verdict); `comparison between pointer and integer`;
`cast to pointer from integer of different size`; and
`assignment of read-only parameter` for `int a[const N]`.

**Accepts-invalid fixed on the way.** `void f(int a[const 2]) { a = 0; }`
compiled silently: the parser discarded the qualifiers inside the brackets,
and upstream's read-only checker (`b76cc9264`, kept through the agent's
`pointer_quals` series) treats an adjusted array parameter as never
top-level const. `ParamDecl.adjusted_cvr` now carries them and both
parameter sites read it.

**Type spelling.** `invalid operands` messages spelled operand types through
`Display` (`unsigned long`, `__attribute__((vector_size(16))) int`); they
now use GCC's leaf spellings and declarator chains (`long unsigned int`,
`__vector(4) int`, `int (* const*)[3]`). A vector compared with a pointer
reported a cascade (the comparison was typed as the vector); it now reports
once and leaves the invalid expression untyped (`None`).

## Operand types after the integer promotions

Found while red-teaming upstream's operand diagnostics (#993, `01a7345df`):
"invalid operands to binary" named operand types before the integer
promotions. GCC's `build_binary_op` applies them first (C11 6.5.5-6.5.14),
so gcc-16 reports `short % 1.5` as `'int'`; lccc said `'short int'`. On a
16-line probe, 13 lines differed: char, signed and unsigned char, unsigned
short, `_Bool`, an enumeration (`'unsigned int'`), a packed enumeration, a
narrow bit-field, a 40-bit `unsigned long` bit-field (GCC keeps the
bit-field's own type, `'long unsigned int:40'`), and compound assignment
(`s %= 1.5`). When `binary()` reports invalid operands,
`check_binary_operands` re-spells them with their promoted types, using the
bit-field-aware promotion `-Wformat` already had (#996), and `Operand`
carries the width GCC prints for a wide bit-field. Promotion never changes
the verdict, so valid expressions pay nothing for it. The probe is now a case
in `check_operand_diagnostics.sh` (gnu90/gnu17/gnu23, record checked against
gcc-16 as well).
