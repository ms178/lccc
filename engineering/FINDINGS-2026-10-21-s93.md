# S93 findings (2026-10-21, on ms178/lccc main 771f8a3fa)

Every claim below is backed by a test, a gate or a measurement named next to
it. Performance numbers are Callgrind instruction counts (Ir; the VM has no
PMU), on the deterministic input built by `scripts/zstd_eval/setup.sh` (first
1.5 MiB of zstd 1.5.7's sorted C sources, sha256 `ee05dd84…a327`).

## 1. `always_inline` was not honoured for large bodies (GCC semantics bug)

**Defect.** `callee_data_for` refused any `always_inline` callee above the
500-instruction / 500-block "relaxed" tier, and Phase 0 drained clone-born
sites with a flat counter (2 × entry sites + 16). The fallback passes are
instruction-metered (200 + 400), so bodies exposed late could never fit.
GCC inlines `always_inline` unconditionally (a failure is a hard error).
Callee sizes grow across inliner rounds (inner helpers inline first:
`ZSTD_decodeSequence` 253 → 432 → 851 IR instructions), so a body could pass
the cap early and fail it later.

**Effect on zstd.** Every `FORCE_INLINE_TEMPLATE` specialisation was lost:
`ZSTD_compressBlock_opt_generic` (803 IR instructions; `optLevel` never
propagated), `ZSTD_compressBlock_lazy_generic` (22 wrappers with constant
`searchMethod`/`depth`/`dictMode`), `doubleFast_dictMatchState_generic`,
`HUF_compress1X_usingCTable_internal_body_loop` (constant unroll/flush
flags, every compression level), `ZSTD_decodeSequence` (split-literal
paths). Out-of-line template bodies in the CLI: 7 before, GCC 0.

**Fix.**
- Admission: only a resource guard (16 384 instructions / 4 096 blocks,
  more than 10× every real body seen) may refuse an `always_inline` callee.
  The 500 tier still governs ordinary statics of section-attributed callers
  (it is shared with that unrelated policy, so it was not simply raised).
- Phase 0 spends its counter only on callees on a cycle of the **full
  direct call graph** (iterative Tarjan, O(V + E)). Acyclic expansion
  terminates by itself: each drained body exposes only callees strictly
  below it in the call DAG. The full graph rather than the `always_inline`
  subgraph is required: later ordinary inlining composes edges
  (X → Z → Y becomes X → Y), and every cycle such composition can create
  already exists in the full graph. Devirtualisation runs before the graph
  is built, and within a run indirect calls never become direct.
- `PHASE0_CALLER_GUARD_INSTRUCTIONS` (262 144) bounds adversarial
  diamond-DAG fan-out.

**Tests** (`src/passes/inline.rs`): SCC classification (self, mutual,
3-cycle, acyclic, declaration); admission above the old cap and refusal
above the guard; a HUF-shaped fan-out (1 entry site → 40 template sites of
30 instructions) drained completely. The joint-fixpoint test now reaches the
second pass through a recursive template: after this fix that is the only
way left to get there. Its negative control still discriminates.

## 2. TZCNT was gated on LZCNT instead of BMI1 (x86-64 and i686)

TZCNT (F3 0F BC) is a BMI1 instruction; LZCNT (F3 0F BD) is ABM. Neither
faults on CPUs lacking the feature: they execute as BSF/BSR and return wrong
results. LZCNT-only CPUs exist (AMD K10, Bobcat, Jaguar), so `-mlzcnt` code
computed garbage for `Ctz(0)` there. GCC 16.2 gates `tzcnt` on `-mbmi`:

| flags | GCC 16.2 | main | now |
|---|---|---|---|
| `-m32 -mlzcnt` | `rep bsf` | `tzcnt` ✗ | `bsf` ✓ |
| `-m32 -mbmi`, `-mbmi`, v3 `-mno-lzcnt` | `tzcnt` | `bsf` ✗ | `tzcnt` ✓ |
| v3 `-mno-bmi` | `rep bsf` | `tzcnt` ✗ | `bsf` ✓ |

The x86-64 emitter had two Ctz paths gated wrongly (the accumulator path in
`alu.rs` and the register-direct path in `float_ops.rs`). i686 had no BMI1
bit at all: `resolved_codegen_bmi1()` extends the codegen permission to
i686, while `__BMI__` and the ANDN-dependent middle-end choices stay on the
x86-64-locked `resolved_bmi1()` (i686 lowers no ANDN/BLSR).

`rep bsf` (GCC's choice without BMI1) was considered and declined: it buys
nothing on CPUs without BMI1 (it *is* BSF there), and our zero handling
does not depend on TZCNT semantics.

**Gate** `check_i686_integer_isa_parity.sh` (rewritten): ownership per form,
vetoes per form, macro contract, a runtime check of all three forms, and a
GCC oracle section comparing the BSF/TZCNT and BSR/LZCNT class on 8 flag
sets (8/8 match GCC 16.2.0). The previous gate asserted the defect.

## 3. Narrow bit operations were not width-exact

The IR contract (`src/ir/ops.rs`) defines Clz/Ctz of zero as the operand
width, and upstream's own analyses (`bit_idioms_observe`: `Ctz(x) == width`
→ `x == 0`; `bit_idioms_demand`: `reverse_bits() >> (64 − width)`;
#893's `bit_idioms_count_merge`: `min(ctz x, ctz y) = ctz(x | y)`) rely on
it. Two components disagreed:

- **Constant folder** (32-bit evaluation of sub-32-bit types): Clz(u8 1)
  = 31 (should be 7), Ctz(u8 0) = 32 (8), Popcount(i8 −1) = 32 (8; the
  sign-extended operand leaked), Bswap(i8) swapped 64 bits (identity),
  BitReverse(u8/u16) reversed 32 bits. Each is a constant-vs-runtime
  disagreement that changes with optimisation level. Fixed by evaluating
  every operation on the operand masked to its width. Tested exhaustively
  against Rust's native `u8`/`u16` operations for all 2 × 65 792 inputs,
  zero- and sign-extended.
- **x86-64 emitter**: `movzbl; tzcntl` gave Ctz(u8 0) = 32. Now a stop bit
  (`orl $0x100` / `orl $0x10000`) makes the scanned value nonzero, so zero
  yields 8/16; the baseline BSF path becomes **branchless** (was
  test/jnz/mov/jmp/bsf) and the zero-extension disappears (bits above the
  stop bit can never be the lowest set bit). i686 already used the stop bit.
  Proven-nonzero narrow Ctz also drops its zero-extension (the lowest set
  bit lies in the low lane).

## 4. `__attribute__((target("...")))` was parsed and dropped

zstd's `*_bmi2` clones compiled to the baseline ISA (0 BMI instructions vs
GCC's 15–136 per clone). Now: per-function ISA scoping in the x86 backend
(restored after each function), and GCC's inline refusal (callee features
must be a subset of the caller's). Gate `check_target_attribute_isa.sh`:
scoping before and after the attributed function, the call kept by a plain
dispatcher, absorption by a covering caller, and the runtime result equal
to GCC 16.2.

## 5. Upstream review (verdicts with reasons)

- **5675eb4c4 / #893 `narrow_copy_fold` `%bpl` extension exemption: AGREE**
  (verdict reversed from S92). The use-window scan stops at every write to
  the source family, and `leave` is modelled as an RBP write
  (`types.rs`: `leave` → writes RSP|RBP), `popq %rbp` as a classified
  destination. A frame-pointer RBP therefore cannot be redefined inside a
  folded window. Main's implementation (per-function cached proof,
  `movslq` identity widening) supersedes mine; I dropped my memo.
- **Same pass, missing guard: fixed.** Main can rename `%rbp` *into* a
  memory operand (`movq %rbp,%r11; movq 8(%r11),%rax` → `movq 8(%rbp),%rax`).
  Main's own tests treat `N(%rbp)` as a frame-pointer contract marker, so
  the fold manufactures frame evidence for later rounds, and slot-keyed
  passes then see a heap dereference as a stack slot. `eliminate_move_relays`
  already refuses this (`move_relay_never_creates_an_rbp_memory_operand`);
  `narrow_copy_fold` now does too.
- **#893 `bit_idioms_count_merge`: AGREE.** Checked case by case (above).
  Its narrow-width rewrites are only correct at run time on x86-64 with the
  §3 emitter fix.
- **#893 `bit_idioms_guards`: no defect found** in the reviewed rewrites
  (conditional negate requires a {0,1} proof, not truthiness).
- **d88027fcb sidecar flags:** `run_regression.py` now prepends `-O2` to
  sidecars without an `-O` level, so my explicit `-O2` was redundant churn;
  took main's form.

## 6. S94 (rebased on aac1c1e3a: #896, #900)

- **#896 (i128 atomics as call points): AGREE, and it superseded mine.**
  Both series fixed the same miscompile in `instruction_is_call_point`.
  Main's single arm also covers `AtomicInc`, and a 16-byte test-and-set
  would lower to `__atomic_exchange_16`, so mine (which excluded
  test-and-set and missed `AtomicInc`) was dropped in the rebase. My unit
  test `sixteen_byte_atomics_are_call_points` now pins main's semantics for
  all five kinds. Main keeps the investigation doc as a resolved record;
  I had deleted it, and keeping it is right because it records three
  disproved hypotheses. `check_atomic16_runtime.sh` here already runs its
  runtime half at -O1/-O2/-O3, which closes that doc's open follow-up.
- **#900 (dual-layout metric peepholes run concurrently): AGREE.** The
  worker is a scoped thread, so it inherits no thread-local state. No
  peephole path reads one: there is no ISA, TLS-dialect or pointer-width
  query in `peephole/`, so the pipeline is a pure function of the text,
  `RaConfig` and the size flag, as the PR claims. The new peephole code
  here keeps that property. The only thread-local touched is the test-only
  `test_skips`, which no test applies to the pair entry point.
- **#893 `observe` (demand-driven compare walk): DISAGREE in part; fixed.**
  It peeled invertible producers unconditionally. When a single-cycle
  producer (XOR/ADD/SUB/AND/OR/NOT/NEG/shift/rotate/select) has other
  users, it still executes. The peel then saves nothing, a `mask != all`
  result even mints a new AND, and the root's live range is stretched
  across the compare. In `bucket` (`hb = 31 - clz(x|1); ... if (hb == 0)`)
  that cost an extra register and blocked the highbit `bsr` cancellation.
  The rule now is:
  - a peel through a shared single-cycle producer marks the test `shared`;
  - a shared test keeps only the direct one-instruction materialisation
    (`And 1` or `LShr 31`, which is cheaper than cmp+setcc+movzx);
  - multi-cycle producers (Mul, UDiv, counts, byte/bit reversal) still
    peel when shared, because the compare leaves their latency chain;
  - `cancel` (`(a op k) == (b op k)`) requires one side to die or to be
    multi-cycle.
  Five unit tests cover this.
- **Phase ordering: late renames exposed uncancelled identities.**
  `rename_chain_into_copy` (phase 3d) and the aliasing producer retarget
  (3c) run after the local fixpoint. The emitter's
  `xor $K,%a; mov %a,%b; xor $K,%b` becomes adjacent only after the chain
  is renamed into `%b`. The highbit cancellation is now a helper used both
  by `combined_local_pass` and by a sweep that runs only when 3c or 3d
  renamed something (linear, behind the `combined` skip knob). An
  end-to-end test, `pair_exposed_by_the_late_chain_rename_cancels`, drives
  the whole pipeline on the emitter's real text.
  `bucket` result: a bare `bsrl` and 14 hot-path instructions; GCC 16.2
  needs 16 and keeps `bsr; xor $31; sub`.

## 7. S95: rebase onto 8f1486fde (#901, #902, #906)

- **#902 `elide_readonly_local_memcpys`: miscompile; fixed.** It proved
  the *local* read-only and re-rooted its readers at the copy's source
  where they stood, so every write to the source between the copy and a
  read leaked into the copy. Pristine main 8f1486fde prints
  `103 50 134 1001 11 85` for `tests/regression/inline_elide_copy_source_write.c`;
  GCC 16.2 and Clang 23.1.3 print `7 1 30 3 11 9`. The shapes are
  ordinary C: a field store, a store through an aliasing pointer, a
  loop-carried update, a conditional write, and a by-value struct
  parameter whose caller-side object the body writes (`1001`).
  The fix is scalar replacement at the copy (as GCC's SRA does it): every
  reader is *moved* to just after the copy and re-rooted there, so it
  reads the bytes at the instant the copy did. Side conditions: constant
  in-bounds offsets (a moved load cannot fault only on bytes the copy
  dereferenced), no segment override, no reader before the copy, and copy
  chains snapshotted at their first copy. Two further holes closed on the
  way: a second copy into the local from the *same* source value was
  exempt from the escape scan (matched by `(dest, src)`; now by
  position), and the local's address used as a `GetElementPtr` offset was
  not an escape. #902's
  `surviving_copy_reading_an_elided_local_is_rerooted` asserted the
  unsound contract (a surviving copy re-rooted to read the source late);
  it now asserts that the local it reads is kept. Six unit tests cover the
  new rules. The elision still fires where it should: `run_control` is
  `movl (%rdi),%eax; addl 4(%rdi),%eax; ret`.
- **a7a8a6500 (sret_copy_elision source writes): AGREE; merged with
  mine.** It is sound for the case it targets, and more permissive than my
  phase 2 was: stores to the source are allowed unless they fall between
  the copy and the last re-rooted read. I kept its phase 2 and replaced
  only its phase 1, which still had no NRV side condition (the
  `sret_slot_aliases_argument` miscompile is still live on main). Two
  refinements: a volatile load is now opaque (upstream re-rooted it at a
  different object; GCC and LLVM both refuse), and `precedes` takes one
  lazily built `CfgAnalysis` instead of rebuilding the CFG and dominator
  tree on every (write, copy) query. Its module docs claimed the copy must
  be the destination's only write and that every source write must
  dominate the copy; they now describe the code as written.
- **0b3f8be23 `CCC_PEEPHOLE_BUDGET`: DISAGREE; removed.** The 512 KiB /
  20k-line cutoff skipped `eliminate_redundant_zero_extend` in zstd's
  hottest TUs (`zstd_lazy` 90k lines, `zstd_compress`, `zstd_opt`,
  `huf_decompress`) and printed a warning on every large compile. The
  pass is one linear scan. Measured with `CCC_NO_PEEPHOLE=1` (which
  returns right after it): `zstd_lazy.c` 12.0-13.0 s on and off. A
  145k-line single function: about 7 min both ways, all of it in the IR
  pipeline, and 36.8 KB less output with the pass on. The commit's
  "solves 84% of compile time" cannot be this pass, which runs twice and
  gates nothing else. Removing the budget saves 12 instructions in
  `zstd_opt` and 8 in `zstd_lazy` (relay copies around `movzbl` compares).
- **Merge defect in my series, fixed.** `i686_scratch_pool` had been
  inserted between `spans_any_call`'s doc comment and `#[inline]` and the
  function itself, so it took both.
- **Debug locations of moved readers.** My first version gave every reader
  moved to a copy the copy's source span, which broke #902's
  `elision_keeps_source_spans_parallel_to_instructions`. The test is
  right: the line that names the field is the one a debugger should stop
  at. A moved reader now keeps its own span. It takes the copy's only when
  its block's span vector is not parallel to the instructions.
- **Duplicate tests from my own series.** bcac0b0af had ported four
  `sret_copy_elision` tests from the open #890; #890 has since landed with
  them, so the rebased tree failed to compile (E0428 x4). The copies were
  identical and are gone. The commit is empty and is dropped.
- Validation after the rebase: full `--lib` 5863 passed, 0 failed. The
  zstd 1.5.7 CLI builds (1,296,040 B, no outlined `FORCE_INLINE`
  template), round-trips 32/32, and the fuzzer exits 0.

## 8. DSE: an earlier store overwritten by several later ones

`E e = {5, 6}` (two `int`s, address passed to a call) lowers to an 8-byte
zero fill followed by both 4-byte field stores. `dse::covered` asked
whether one later pending store contains the earlier store's bytes, so the
zero fill survived (`movq $0, (%rsp)` before the two `movl`s) whenever the
fields were written separately.

`covered` now also accepts a tiling: it collects the same-root pending
entries that overlap the range, sorts them by offset and sweeps a reach
pointer. A gap means not covered. A read between the stores removes every
pending entry it overlaps by even one byte, so every remaining entry proves
that its own bytes are overwritten before anything reads them, and so does
their union. `Pending.size` is the store's definite byte count (the
`access_extent` lower bound), so a masked or partial store never counts for
more than it writes. Offsets use `checked_add`. A zero-length entry never
advances the reach. The common path, where one entry contains the range,
returns before the vector allocates.

Unit tests: two field stores over an 8-byte zero fill remove it. It is
kept if a read sits between them, if the tiling leaves a gap, and in the
overlapping-but-complete case it is removed.

`dz.c`, -O2, instructions per function:

| function | before | after | GCC 16.2 |
|---|---:|---:|---:|
| `f2` (`E t[2] = {{1,2},{3,4}}`) | 11 | 9 | 7 |
| `f1` (`E e = {5,6}`) | 8 | 7 | 7 |
| `fq` (`Q q = {x,2,3,4}`) | 11 | 9 | 9 |
| `fpart` (`Q q = {1,2}`) | 9 | 8 | 8 |

`fpart` keeps the zero fill of `c` and `d`, because nothing else writes
them. GCC's remaining edge in `f2` is store merging (one 16-byte `.rodata`
constant stored with `movaps`). In `f1` and `fpart` GCC also merges, to
`movabsq` plus one `movq`, at the same instruction count.

## 9. S96: clz/ctz zero contract restored; bit-count facts; dead scratch saves

**Defect in my series (fixed): `__builtin_clz/ctz` of zero.** My series
lowered `__builtin_clz`/`__builtin_ctz` straight to `ClzNonZero`/
`CtzNonZero` (citing the C contract: undefined for zero) and rewrote the
`IrUnaryOp` docs to match. The full corpus caught it: two long-standing
tests, `bitop_nonneg_zext` and `bitops_builtins` (August), pin
`clz(0) == ctz(0) == 32` and say why ("the undefined-input cases the
codegen must handle deterministically"). Both failed at every level,
including -O0, and `main` of the first ran a `bsrl` on a constant zero,
because the folder deliberately does not fold a NonZero count of zero
(31e73b71f; I agree with that rule). GCC 16.2 is not a counter-argument:
it passes the same tests only because it folds them.

The lowering is upstream's again. A builtin produces the zero-defined
count, and CVP/`nonzero_guard_refinement` produce the bare forms wherever
control flow proves the operand nonzero. All my other clz/ctz work stays,
because it works on proven-nonzero or zero-defined forms: the BMI1 owner
of TZCNT, the `btsq $32; bsfq` stop-bit `Ctz32`, the highbit peephole and
the guard refinement. `rotate_highbit_idioms.c` still gets its bare `bsr`,
because its highbit uses sit under `if (x)`, and its header comment now
says so. Results: `bitop_nonneg_zext`, `bitops_builtins` and
`rotate_highbit_idioms` match GCC 16.2 at O0-O3 and `-m32`, and the
constant `main` folds to `xorl %eax, %eax; ret`.

**Missed optimization: re-extending a bit count.** `redundant_ext`
recorded no fact for `bsf/bsr/popcnt/lzcnt/tzcnt`, so
`(long)__builtin_ctz(x)` kept a `movl %eax, %eax` after
`btsq $32; bsfq`. A 32/64-bit count writes the whole register with a
value in 0..=64: upper half clear, fits in a byte, and equal to the sign
extension of its low 8/16/32 bits. The new rule establishes all of these.
POPCNT/LZCNT/TZCNT are defined for every input. BSF/BSR appear only where
the source is nonzero (proven NonZero, a guarded arm, or a stop bit), and
user inline asm is opaque to the pass. The 16-bit forms write only `%ax`
and establish nothing. Tests: the stop-bit shape, the popcount
re-extension chain, and the 16-bit, label and overwrite negatives.

**Missed optimization: dead scratch saves.** The baseline SWAR popcount
(and other fixed-scratch emitter sequences) wraps its body in
`pushq %rcx ... popq %rcx` (`%rdx` too on the 64-bit path), whether or not
the register is live. GCC 16.2 calls `__popcountdi2` for the same source,
so the inline SWAR already wins, but the save costs two stack accesses
and, worse, makes the whole body a barrier for every offset-tracking
pass. The new `eliminate_dead_scratch_saves` (push_pop.rs; skip name
`dead_scratch_saves`) drops a pair when `R` is dead after the `pop`
according to the file liveness solution, and the span is blind to the
`%rsp` shift. "Blind" means: no label, branch, call, `ret`, inline asm,
`pushf`/`popf`, CFI or `%rsp`/`%esp` operand inside, inner push/pop
balanced, and no CFI adjustment right after the `pop`. Callee-saved
registers are live at `ret` in that solution, so a prologue save never
qualifies. With `# LCCC_RET_RDX 1` (a 16-byte return) a `%rdx` save is
kept. Removals only shrink live sets, so one solution per call stays
conservative for every later query. In a loop, the next iteration's
`push` is the only reader of `R`, so a second query
(`live_after_dropping_region` restricted to the push line) discounts that
one read. Only the push line is neutralised: a read of `R` inside the span
before any write there still keeps the save, because the next iteration
would see the span's value instead of the restored one. That case has a
test. Measured at -O2, baseline x86-64 ("before" =
`CCC_PEEPHOLE_SKIP=dead_scratch_saves` on the same binary, except the ctz
row, which is the `redundant_ext` change):

| function | before | after | GCC 16.2 |
|---|---:|---:|---|
| `(long)__builtin_ctz(x)` | 5 | 4 | `xorl; rep bsf` (3) |
| `(long)__builtin_popcount(x)` | 19 | 17 | call `__popcountdi2` |
| `__builtin_popcountll(x)` | 25 | 21 | call `__popcountdi2` |
| popcount-sum loop | 29 | 27 (no stack traffic per iteration) | call per element | Unit tests: the SWAR32 body, nested
saves under both `RET_RDX` markers, a live register, callee-saved,
`%rsp`-relative, a label, a call, a mismatched restore, CFI inside and
after, and an inert `.loc`.

**Upstream since 8f1486fde (#905, #908): AGREE.** RS-1 is a real
reproducibility bug: RISC-V iterated a `std` `HashMap` seeded per
process, so the surviving duplicate label varied between runs. The fix
(`FxHashMap`) and the gate (three compiles, one hash) are right. The
metric-pair split is output-neutral by construction, and its
saturation measurement (1.0023) answers the throughput question I would
have asked. The rebase was clean, and the per-backend pair overrides
match upstream exactly.
