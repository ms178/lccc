# x86 ISA permissions and the SIMD ABI

This document states the contracts lccc keeps for x86 instruction-set
permissions (what code a function may contain) and for passing SIMD values
between functions (what a caller and callee agree on). Each rule names the
code that implements it and the gate that enforces it. GCC 16.2 is the
reference: every rule below was measured against `gcc-16`, and the gates
re-measure it where GCC is installed.

## 1. Permission layers

A function's permission is resolved in three layers. Each layer can only
narrow what the next one may grant: nothing outside the three ever adds an
instruction set.

1. **Translation unit.** The driver resolves `-march=` and `-m[no-]FEATURE`
   into `common::x86_features::EffectiveFeatures`
   (`Driver::effective_x86_features`) and publishes GCC's explicit mask
   with it (`Driver::x86_explicit_feature_bits`, §1.2).
2. **Function.** `__attribute__((target("...")))` keeps its options in
   source order (`ir::module::normalize_target_features` neither sorts nor
   deduplicates) and `backend::x86::isa::function_feature_bits` folds them
   over the TU's features. Every consumer reads that one fold: code
   generation (`X86Isa::with_target_features`, `ScalarIsa`), intrinsic
   permission (`function_feature_permitted`), F16C conversions, the
   inliner and the vector passes.
3. **Code generation ceiling.** `backend::x86::isa::X86Isa` carries the
   vector classes the x86-64 backend can emit (`simd`, `sse41`, `avx`,
   `ymm`, `fma`, `movbe`, `cx16`). `normalized()` enforces the implications
   (`ymm` ⇒ `avx` ⇒ `sse41` ⇒ `simd`). Integer extensions (POPCNT, BMI,
   BMI2, LZCNT) are resolved per function from the same features.

Over-granting is the dangerous direction. GCC 16 removed AES from Westmere
through Broadwell, because Pentium and Celeron parts of those generations
lack AES-NI, and a profile that kept `__AES__` would steer
`#ifdef __AES__` code into SIGILL on them.

### 1.1 The CPU and option table

`backend/x86/arch_table.rs` is generated by `scripts/gen_x86_arch_table.py`
and is never edited by hand. It records, all measured from GCC 16.2:

* for every name GCC lists for `-march=`: whether GCC accepts it on
  x86-64, its full `X86Feature` set (plus GCC's ABM state) read from
  `gcc-16 -march=NAME -dM -E` in its widest mode (CMOV from GCC's code for
  a `max()`), its macro-only extensions (`__PRFCHW__`, `__SHA512__`, AMX,
  ...), the features it has only through ABM (`abm_derived`), and its
  CPU-name macros (§1.6);
* for every ISA option: the mask its positive form sets, the mask
  `general-regs-only` clears and the mask its `no-` form unsets, each
  measured from a base where every feature is explicitly denied (so GCC's
  override implications cannot leak in), and the override implications
  themselves (`X86_IMPLIED`: SSE brings MMX, SSE4.2 POPCNT, ABM LZCNT,
  unless the implied feature was named);
* for every macro-only extension: the features whose removal removes it
  (`requires`): AVXIFMA leaves with `-mno-avx2`, SHA512 only with
  `-mno-avx`, CMPCCXADD with nothing.

Before writing, the generator checks the driver's `-march=CPU -mno-N`
model, the CPU's features minus N's unset mask (minus `abm_derived` for
`abm`), against GCC for every CPU, mode and negatable option: 8772 cases.
`--check` re-measures GCC and fails on any difference, so a GCC update
cannot silently change permissions.

The driver uses the table in both directions. Every `-march=` name goes
through its row (`Driver::enable_x86_arch_row`); the hand-kept profiles it
replaced had drifted (Sapphire Rapids without AVX-VNNI and AMX, Tiger Lake
without AVX512VP2INTERSECT). Every `-m` ISA option applies its measured
mask after its own bookkeeping (`Driver::apply_x86_option_mask`); the
hand-kept implications it replaced kept all AVX-512 subsets under
`-mno-avx2`, FMA and F16C under `-mno-avx`, and missed PCLMUL for
`-mvpclmulqdq` and SSE4.2 for `-msse4`. GCC's command-line cancellation
(a later `-mX`/`-mno-X` deletes every earlier spelling with what it
implied) happens before either.

### 1.2 `target("...")` semantics (GCC 16.2, measured)

`function_feature_bits(tu, tu_explicit, options, x86_64)`:

* **Options apply in order**, each through its measured mask: `NAME`
  sets, `general-regs-only` clears, `no-NAME` unsets.
  `avx512bmm,no-avx512bmm` therefore keeps the AVX512BW and AVX512F that
  `avx512bmm` set, as in GCC; `avx2,no-sse4.1` keeps SSE3 and SSSE3.
* **`arch=CPU` replaces** the features with the CPU's row and forgets what
  was explicit: under `-mpopcnt`, `target("arch=x86-64")` has no POPCNT,
  and options left of the last `arch=` are lost (`avx2,arch=x86-64` is
  SSE2, `no-sse,arch=haswell` is AVX2). The review suggestion to keep
  `-m` grants inside `arch=` functions was rejected for this reason. An
  option after it that removes ABM also removes what the CPU has only
  through ABM (`arch=amdfam10,no-abm` has neither POPCNT nor LZCNT).
* **Then the override implications**, unless the implied feature is
  explicit, from the command line or an option: `-mno-popcnt` with
  `target("sse4.2")` has no POPCNT.
* **Errors** use GCC's wording: a repeated `key=`, an unknown or `native`
  CPU, `arch=generic` (allowed only for `tune=`), and a 32-bit-only CPU
  on x86-64. `target` together with `target_clones` is diagnosed, and the
  `target_clones` attribute is ignored, as in GCC.

### 1.3 Intrinsic permission

`function_feature_permitted(options, feature, x86_64)` asks the fold
whether the function has `feature`, plus the one conjunct GCC's builtin
masks add to the feature graph: AES, PCLMUL and GFNI intrinsics also need
SSE2. `no-sse2` leaves their bits set, so `target("aes,no-sse2")` rejects
`_mm_aesenc_si128` (naming the missing SSE2), and `target("no-sse2,aes")`,
where `aes` grants SSE2 back, accepts it. The 128/256-bit VNNI dot
products are also legal through their EVEX form (AVX512-VNNI with
AVX512-VL on the AVX2 class, `function_evex_vnni_permitted`).

The intrinsic headers for scalar integer extensions (`bmiintrin.h`,
`bmi2intrin.h`, `lzcntintrin.h`, `popcntintrin.h`) are portable by design.
Outside a function granted the extension they compile to a correct
sequence instead of being rejected, so they never emit an instruction the
function lacks (GCC rejects the call). A header cannot make that choice
from TU macros, because `__BMI2__` ignores a function's `target()`. So on
x86-64 `_pdep_*`/`_pext_*` lower to `IntrinsicOp::Pdep`/`Pext`, and the
backend picks per final function: hardware `pdep`/`pext` where BMI2 is
enabled, else an exact loop over the mask's set bits (`emit_pdep_pext`).
i686 has no BMI2 code generation, so there the header itself uses
portable C. The instruction contract and the semantics against GCC are
checked by `check_x86_scalar_intrinsics.sh`, including `target("arch=")`
callers under `-mbmi2`.

**Inlining** of a callee with `target(...)` needs only that its folded
features are a subset of the caller's. GCC also requires equal
`arch=`/`tune=`, which forbids inlining a `target("bmi2")` helper into an
`arch=haswell` caller that has BMI2; lccc's permission is the feature set,
so that rule would only cost code quality.

A callee without `target(...)` is judged by what its IR depends on, recorded
during lowering in `IrFunction::x86_isa_needs` (`X86IsaNeeds`):

* `relied`: features whose permission check passed, so the body holds an
  intrinsic only they allow. It may inline only into callers that hold them.
  Everything else is ISA-neutral and is lowered under the final function's
  set: `_mm_popcnt_u32` inside `target("arch=x86-64")` in a haswell unit
  inlines and becomes the portable sequence.
* FP or SIMD values need SSE/SSE2 (as far as the unit has them) and x87, so
  such a body never moves into a `general-regs-only`, `no-sse2` or
  `no-80387` caller.
* `deferred`: the 512-bit intrinsics are `always_inline` bodies in
  `lcccsimd.h` without GCC's per-function `target`. In a unit that lacks the
  extension, a plain `always_inline` body records the requirement instead
  of rejecting it. Inlining settles the part the caller grants
  (`X86IsaNeeds::absorb`); another plain `always_inline` body passes the
  rest on. Whatever survives inlining is an error before code generation:
  "in function 'f': `__lccc_simd512_i_vpaddb512` requires avx512f,
  avx512bw (...); inlining failed in call to 'always_inline'
  '_mm512_add_epi8': target specific option mismatch". GCC gives the same
  verdict for a plain caller and accepts a `target("avx512bw")` one. Unlike
  GCC, lccc also accepts the requirement passing through a user's own plain
  `always_inline` helper, the way the header's wrappers nest.

### 1.4 `target_clones`

`target_clones::resolve_clone_spec` keeps GCC's dispatch priorities
(`gcc_prio`). For `arch=` clones it departs from GCC in one deliberate
way: GCC tests `__builtin_cpu_is`, whereas lccc probes the CPU's whole GCC
feature set, including its whole AVX-512 set, which is also the set the
clone's code is confined to. A Nehalem has every x86-64-v2 feature but no
PCLMUL, so it does not run the `arch=westmere` clone, and an
`arch=sapphirerapids` clone needs AVX512-FP16 and BF16.

**AVX-512.** lccc emits no AVX-512 code. Every AVX-512 CPU, including
`x86-64-v4`, therefore grants exactly the v3 code permission (unit test
`avx512_cpus_grant_exactly_v3`); the features still decide dispatch, so
adding EVEX code generation later changes no dispatch decision.

### 1.5 i686

The x86-64 vector ceiling stays `X86Isa::NONE` on i686. The i686 backend
implements only a small subset of the vector families, and opening the
ceiling without them would miscompile. The i686 SSE levels follow the same
fold, and after code generation `first_target_attribute_leak` checks that
no function contains an instruction above its own grant, including above
an `arch=` CPU's levels. The integer ISA macros follow the CPU on i686 as
on x86-64 (`-m32 -march=haswell` defines `__BMI__` and `__MOVBE__`): the
BMI1 intrinsics are plain C and no header keys on `__MOVBE__`, so every
path they select compiles.

### 1.6 Predefined macros

The ISA macros (`__AVX2__`, `__BMI2__`, ...) follow the resolved
permission (§1). GCC also names the CPU:

* `-march=X` defines X's measured `-march=` macros. The default `x86-64`
  (and v2 to v4) define `__k8`/`__k8__`.
* The tuning CPU defines its `__tune_*__` macros. That is `-mtune=Y` if
  given; otherwise the `-march=` CPU, except that `x86-64*` tunes generic
  and defines none.
* `__athlon_sse__`-style companions need SSE (`-march=athlon-4 -mno-sse`
  drops them).
* `native` and `generic` define no CPU name. lccc's `native` is
  feature-detected, and lccc has no CPUID-to-GCC-name table, so it would
  have to guess.

`gen_x86_arch_table.py --check` verifies the two defaulting rules against
GCC for every CPU. `-mno-mmx` withdraws `__MMX__`, as GCC does, while the
MMX intrinsics stay (lccc emulates them without the MMX registers). One
deliberate difference: with the SSE register file off (`-mno-sse`,
`-mno-sse2`, `-mgeneral-regs-only`) GCC still defines `__AES__`,
`__PCLMUL__` and `__GFNI__` but rejects their intrinsics; lccc's macros
only announce intrinsics that compile. On i686, lccc keeps upstream's unconditional
`__i686`/`__i686__` (the `i686-linux-gnu-gcc` spelling).

`__SSE_MATH__`/`__SSE2_MATH__` state which scalar float math the code
generator does in SSE; the ISA level alone doesn't determine it. x86-64
does all of it in SSE. The i686 backend does F32 in SSE only with SSE2,
and F64 always on x87 with declared-type rounding (each result is rounded
to `double` in memory, so `__FLT_EVAL_METHOD__` stays 0). So on i686,
`__SSE_MATH__` follows SSE2 and `__SSE2_MATH__` is never defined. These
are the macros GCC 16.2 gives its own F32-in-SSE, F64-on-x87 mode
(`-m32 -msse -mno-sse2 -mfpmath=sse`). The previous Clang-style pair told
code keyed on `__SSE2_MATH__` that doubles never touch x87.

## 2. SIMD calling convention

* **`__m64`** is GCC's 8-byte vector type. On x86-64 it is passed and
  returned in `%xmm0`. On i686 lccc follows GCC `-mno-mmx` (memory),
  because GCC with MMX returns `__m64` in `%mm0` without `emms`, which
  corrupts later x87 code.
* **Vectors of at most 8 bytes** are returned as packed bits on x86-64.
  Wrappers (`?:`, comma, statement expressions, same-size vector casts)
  spill the packed value once instead of forwarding it as an address.
* **SSE1-only targets** (`-mno-sse2 -msse`) move 8-byte SSE-class values
  between XMM and memory with `movlps` (SSE1), never `movq`/`movsd`
  (SSE2). Register copies use `movaps`. GPR↔XMM moves go through a stack
  slot.
* **i686 fastcall** passes native vectors in `%xmm0-2`/`%ymm0-2` exactly
  as cdecl does (`call_abi::i386_vector_reg_bytes`); vectors never occupy
  the ECX/EDX chain.
* **Dirty upper YMM state** is cleared with `vzeroupper` before ordinary
  calls and returns, as GCC and Clang do.

`check_public_simd_abi.py` runs every shape across the lccc/GCC
caller/callee pairings. `check_legacy_sse_permissions.py` checks the
SSE1/SSE2 boundary of every public intrinsic.

## 3. Call-frame information

Code generation never writes `.cfi_*` directives. `backend/cfi_synth.rs`
derives all CFI after the peephole pipeline from the final instructions
(`push`, `pop`, `sub`/`add`/`lea` on the stack pointer). A hand-written
directive in a function body makes the frame-pointer-omission callee-save
pass give up, so such a function would compile differently with and
without unwind tables. `check_cfi_invariants.sh` compiles every fixture
with and without `-fasynchronous-unwind-tables` and requires identical
instructions.

**modeled, not measured on hardware**: the development VM has no PMU, so
they show executed-instruction count, not cycles. Microarchitectural
claims rest on llvm-mca and the vendor optimization manuals.
